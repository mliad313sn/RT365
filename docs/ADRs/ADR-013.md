# ADR-013 — Per-platform plane guard and simulation isolation
**Status:** Proposed · **Date:** 2026-09-07 · **Deciders (ARB):** ARB, Security & Privacy Board · **Consulted:** MCP Security Agent, Security Architect, Quant Research Lead, Backend Lead · **Provenance:** [Source: 00, 03, 04] / [Committee: REVIEW_C3 OBJ-1, §5; C02 packet C2-D2] / [Open: R-16 worker isolation]

Author: Delivery Orchestrator (AI) · Reviewer: pending (committee) · Approver: pending (ARB). Written after remediation commit `09a6e716` to record the mechanism that commit introduced; it does not approve it.

## Context
ADR-001 enforces the three-plane topology by network policy in deployment and, in-process, by `rtcore.planes.PlaneGuard`, which records every denied crossing in `denies` and calls an `alert_hook` that raises the S1 `plane.deny` alert (auto-action `revoke_agent_identity`). ADR-008 runs backtests on the production pipeline by building a complete simulation platform (`build_sim_platform`) per run, and blueprint 04 allows agents to "run approved simulations", exposed as the `run_simulation` MCP tool.

The MCP Security Agent's challenge (REVIEW_C3 OBJ-1, global R-16 / T-28) reproduced that the `run_simulation` handler built its throwaway platform against the process-global `GUARD`: it cleared `GUARD.denies` and re-pointed `GUARD.alert_hook` at the throwaway platform's alert router. One allowed tool call therefore disabled the live platform's S1 plane-deny alerting and destroyed the deny evidence used by TC-NET-002 — a monitoring-disablement and audit-suppression capability that blueprint 00 forbids to AI/MCP components. The same handler ignored `template`, `strategy_id` and `strategy_version`, so "approved simulations" was not enforced by code.

## Decision
1. **A `PlaneGuard` is a per-platform object, never a shared singleton on any agent-callable path.** `build_sim_platform` constructs `guard = PlaneGuard()` and installs the platform's own `on_deny` hook (which raises `plane.deny` on that platform's `AlertRouter`); the guard is injected into `ExecutionGateway(guard=...)` and stored as `SimPlatform.guard` (`apps/web/web_bff/platform.py`; `services/execution/execution_gateway/gateway.py`). The module-level `rtcore.planes.GUARD` remains as the default for callers that do not compose a platform and is never touched by `build_sim_platform` or `run_sim_backtest` (`libs/core/rtcore/planes.py`).
2. **`run_simulation` runs on a throwaway platform.** The handler calls `run_sim_backtest`, which builds `build_sim_platform(now=start, mode=AccountMode.BACKTEST, bars=0)` with its own guard, alert router, audit store, ledger, simulated broker and intent queue; nothing in it references the live platform's objects, and the live platform's `guard.denies` and alert hook are unchanged after the call (asserted by TC-AI-006).
3. **Approved templates and pinned strategy versions are enforced by the handler and by the closed input schema.** `template` must be in `APPROVED_SIMULATION_TEMPLATES` and match the registry enum; `strategy_id`/`strategy_version` must equal the calling identity's pinned pair and resolve in the strategy registry to a simulatable status; otherwise `ToolDenied("SCOPE")` (`mcp/servers/mcp_servers/tools.py`; `mcp/policies/tool_registry.json`).
4. **Scope of this ADR.** This is the reviewer's option A (private guard). It is proposed as the Gate B condition only; it does not claim process isolation, resource bounds or the catalog's "queued" semantics.

## Alternatives considered (minimum two)
| Alternative | Pros | Cons | Why not |
|---|---|---|---|
| A. Private per-platform guard (chosen for Gate B) | Smallest change; keeps the ADR-008 single code path; testable in-process (TC-AI-006) | Execution-plane classes (gateway, simulated broker) still load in the analytics process (ADR-001 tension); other global singletons found only by inspection; post-hoc resource bounds remain | Chosen as the interim; insufficient alone for Gate D |
| B. Simulation worker process | Structural: no shared memory with the live platform; real pre-emption; cgroup limits; matches the catalog's "queued"; results served by `data_snapshot_id` | More infrastructure; job store and job schema in the registry; result latency | Recommended target for Gate D (R-16 residual); not funded in this cycle |
| C. Remove `run_simulation` from the agent surface | Eliminates the capability class; aligns with C7 "unregistered results are exploratory" | Narrows blueprint 04's allowed capabilities; needs a DECISION_LOG entry | Acceptable fallback if B is not funded before Gate D |
| D. Keep the global guard and reset the hook after the run | No structural change | Leaves a window in which the live hook is disabled; evidence still wiped; race with concurrent calls | Rejected |

## Consequences
- Every composition root must build and inject its own guard; a component that imports `rtcore.planes.GUARD` directly bypasses the platform's alert wiring and must be caught by review (O-45 extends the TC-AI-005 AST scan to handler modules).
- Deny evidence is per platform: gate evidence must cite the live platform's guard, never a simulation's.
- The Gate D conditions in REVIEW_C3 (worker isolation or removal, resource bounds, catalog re-issue) stay open as R-16, O-40 and O-41.
