# ADR-018 — Durable control-state store: one adapter seam, memory and SQLite implementations, journal with tamper evidence
**Status:** Proposed · **Date:** 2026-09-08 · **Deciders (ARB):** ARB, Trading Risk Committee (lease and Kill Switch state), Security & Privacy Board (integrity scheme) · **Consulted:** Trading Domain Lead, Integration Architect, Chief Risk Agent, SRE Lead, Backend Lead · **Provenance:** [Source: 03 stack, outbox/inbox, lease] / [Committee: ADR-010 seam, ADR-014 index durability, ADR-015 decision index, REVIEW_C4 R-23] / [Open: R-05 replicated stores, O-55 journal compaction, O-53 key custody]

Author: build agent E07 (AI) · Reviewer: pending (Trading Domain Lead, Integration Architect) · Approver: pending (ARB; the Product Owner decides, D-039). Written with the commit that introduced the mechanism; it does not approve it. Register item B-1, delegation D-051.

## Context
ADR-010 chose in-memory stores for dev/sim and named the narrow interface behind which Postgres / Kafka adapters would later sit, but no such interface existed: the lease (`dict`), the outbox (`list`), the inbox (`dict`), the gateway's order, idempotency, decision, per-intent and consumed-grant indexes (five dicts and a set) and the Kill Switch activations (`dict`) each lived in a private container. R-05 records that every control invariant those containers carry — fencing tokens never reissued lower, exactly-once business effect under redelivery, one-shot authorisation grants, one live order per intent, an engaged switch at any level — was unproven across a restart; R-23 records that non-ACCOUNT Kill Switch levels vanished with the process. ADR-014 §4 and ADR-015 §4 both deferred the durability of the indexes they rely on to this decision.

## Decision
1. **One `Store` protocol** (`libs/core/rtcore/store.py`): namespaced key/value rows with opaque string values (JSON by convention), `get / put / delete / items`, a monotonic `next_sequence`, a reentrant `transaction`, `verify`, `dump`, `close`. Every `put`/`delete` carries the caller's `correlation_id`.
2. **Two implementations behind it.** `MemoryStore` is the default and the behaviour of every existing test is unchanged. `SqliteStore` (standard library, one file per platform under `build_sim_platform(store_dir=...)`, WAL, `synchronous=FULL`, `BEGIN IMMEDIATE` for writers) is the dev/sim durable backend and the model for the Postgres adapter.
3. **Consumers rewired, interfaces unchanged.** `LeaseStore` (fencing counter = store sequence; acquire/preempt inside a transaction), `Outbox` (rows with a `published` mark; `relay()` hands pending rows to the bus one at a time and marks each after delivery; `pending()`), `Inbox` (result JSON decoded through a `model`), `ExecutionGateway` (tables `execution.orders`, `by_idempotency_key`, `by_client_order_id`, `by_decision`, `consumed_authorisations`, `by_intent`; indexes and the order row written in one transaction; the order row and its outbox event written in one transaction), `KillSwitchService` (table `killswitch.activations`, persist-first unchanged).
4. **Tamper evidence and fail-closed.** Every row carries a digest over (table, key, value, seq) checked on every read; every mutation is appended to a hash-chained journal; `verify()` (run at open) replays the journal and compares it with the state. Any mismatch raises `StoreIntegrityError`, any SQLite error `StoreError`; the gateway wraps `submit`, `retry_submit` and `cancel` so a store failure raises S1 `execution.store_unavailable` and nothing reaches the broker.
5. **Composition root.** `store_dir=None` keeps everything in memory; with a directory the revocation and nonce journals default to the same directory so a restored activation is never paired with forgotten revocations; `authorisation_key` lets a restarted process verify commands its predecessor signed (the vault/KMS path, O-53); `executor_id` names the process.
6. **Not decided here.** Postgres adapter and replication, the bus relay, journal compaction, a keyed (HMAC) or externally anchored journal, durability of the control-plane intent tracker and decision index (see §Consequences), audit-store durability (B-5, E11).

## Alternatives considered (minimum two)
| Alternative | Pros | Cons | Why not |
|---|---|---|---|
| A. One protocol, memory + SQLite, journal with digests (chosen) | standard library only; identical interface; one transaction domain gives the transactional outbox for free; restart and tamper tests run in CI in seconds | SQLite is a single-node file (no replication, no multi-writer across hosts); digests without a key are tamper-evident, not tamper-proof | Chosen for dev/sim; R-05 stays open until the Postgres adapter is evidenced on the deployed topology |
| B. Postgres + Redpanda from the compose stack now | production shape | provisioning is a human act (H-05); tests need containers; the seam would still have to be written first | Deferred: the seam is the prerequisite either way |
| C. JSONL journals per store (the revocation/nonce pattern) | already used; trivially inspectable | no transactions, no atomic multi-row writes, no read-your-writes across processes without re-reading the file; a lease needs compare-and-set | Rejected for the lease and the gateway; kept for revocations/nonces (O-55) |
| D. Pickle/JSON snapshot of the whole platform at intervals | simplest | a crash between snapshots loses the very invariants at stake; no per-row provenance | Rejected |
| E. Keep in-memory, prove durability only at Gate C on Postgres | no work now | every Gate C claim would be made without a test that can run in CI; ADR-014/015 conditions stay open | Rejected |
| Integrity: per-row digest only / chained journal only / HMAC with a process key | cheaper / stronger | row-only misses deletions; journal-only misses live edits until restart; an HMAC key must be persisted and rotated (a secret) | Both digests chosen now; keyed or anchored journal referred to the Security & Privacy Board with O-54 |

## Consequences
- Restart tests exist and run in CI: TC-DUR-001..004, TC-EX-011, TC-KS-010. Evidence stays tagged dev/sim.
- The gateway reads its indexes through the store on every access; a second executor on the same store sees one truth (TC-DUR-002). The in-process cache only avoids re-decoding an unchanged order JSON.
- One SQLite file holds Control-plane and Execution-plane state in dev/sim. In deployment each service owns its schema and its outbox; the table namespaces map one-to-one. The shared file is a dev/sim convenience, not the topology.
- The control-plane intent tracker (`oms.lifecycle.IntentTracker`) and the composition root's decision index (`decisions`) are still in memory. After a restart the permission oracle refuses every pre-restart intent as "unknown to the control plane" (fail closed, TC-EX-011): an in-flight order can be cancelled but not resumed. Resumption needs those two stores behind the same seam (O-33 / R-05 follow-up).
- The journal grows without bound (same as the nonce journal, O-55). `synchronous=FULL` costs an fsync per commit; the full suite measured 9.5 s before and 8.9 s after (177 tests, memory default): JSON encoding of orders behind the seam is not measurable at this size, so one code path costs nothing here.
- `Activation` and every event schema are unchanged (`export_event_schemas --check` green).
