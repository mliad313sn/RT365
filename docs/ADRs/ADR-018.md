# ADR-018 — Durable control-state store: one adapter seam, memory and SQLite implementations, journal with tamper evidence
**Status:** Accepted for dev/sim with conditions (D-058, 2026-09-08; Execution-plane store physically separate from shadow, keyed integrity or anchoring before shadow, cancel-on-restart retained until the Trading Risk Committee advises) · **Date:** 2026-09-08 · **Deciders (ARB):** ARB, Trading Risk Committee (lease and Kill Switch state), Security & Privacy Board (integrity scheme) · **Consulted:** Trading Domain Lead, Integration Architect, Chief Risk Agent, SRE Lead, Backend Lead · **Provenance:** [Source: 03 stack, outbox/inbox, lease] / [Committee: ADR-010 seam, ADR-014 index durability, ADR-015 decision index, REVIEW_C4 R-23] / [Open: R-05 replicated stores, O-55 journal compaction, O-53 key custody]

Author: build agent E07 (AI) · Reviewer: pending (Trading Domain Lead, Integration Architect) · Approver: pending (ARB; the Product Owner decides, D-039). Written with the commit that introduced the mechanism; it does not approve it. Register item B-1, delegation D-051.

## Context
ADR-010 chose in-memory stores for dev/sim and named the narrow interface behind which Postgres / Kafka adapters would later sit, but no such interface existed: the lease (`dict`), the outbox (`list`), the inbox (`dict`), the gateway's order, idempotency, decision, per-intent and consumed-grant indexes (five dicts and a set) and the Kill Switch activations (`dict`) each lived in a private container. R-05 records that every control invariant those containers carry — fencing tokens never reissued lower, exactly-once business effect under redelivery, one-shot authorisation grants, one live order per intent, an engaged switch at any level — was unproven across a restart; R-23 records that non-ACCOUNT Kill Switch levels vanished with the process. ADR-014 §4 and ADR-015 §4 both deferred the durability of the indexes they rely on to this decision.

## Decision
1. **One `Store` protocol** (`libs/core/rtcore/store.py`): namespaced key/value rows with opaque string values (JSON by convention), `get / put / delete / items`, a monotonic `next_sequence`, a reentrant `transaction`, `verify`, `dump`, `close`. Every `put`/`delete` carries the caller's `correlation_id`.
2. **Two implementations behind it.** `MemoryStore` is the default and the behaviour of every existing test is unchanged. `SqliteStore` (standard library, one file per platform under `build_sim_platform(store_dir=...)`, WAL, `synchronous=FULL`, `BEGIN IMMEDIATE` for writers) is the dev/sim durable backend and the model for the Postgres adapter.
3. **Consumers rewired, interfaces unchanged.** `LeaseStore` (fencing counter = store sequence; acquire/preempt inside a transaction), `Outbox` (rows with a `published` mark; `relay()` hands pending rows to the bus one at a time and marks each after delivery; `pending()`), `Inbox` (result JSON decoded through a `model`), `ExecutionGateway` (tables `execution.orders`, `by_idempotency_key`, `by_client_order_id`, `by_decision`, `consumed_authorisations`, `by_intent`; indexes and the order row written in one transaction; the order row and its outbox event written in one transaction), `KillSwitchService` (table `killswitch.activations`, persist-first unchanged).
4. **Tamper evidence and fail-closed.** Every row carries a digest over (table, key, value, seq) checked on every read; every mutation is appended to a hash-chained journal; `verify()` (run at open) replays the journal and compares it with the state. Any mismatch raises `StoreIntegrityError`, any SQLite error `StoreError`; the gateway wraps `submit`, `retry_submit` and `cancel` so a store failure raises S1 `execution.store_unavailable` and nothing reaches the broker.
5. **Composition root.** `store_dir=None` keeps everything in memory; with a directory the revocation and nonce journals default to the same directory so a restored activation is never paired with forgotten revocations; `authorisation_key` lets a restarted process verify commands its predecessor signed (the vault/KMS path, O-53); `executor_id` names the process.
6. **Not decided here.** Postgres adapter and replication, the bus relay, journal compaction, a keyed (HMAC) or externally anchored journal, durability of the control-plane intent tracker and decision index (see §Consequences), audit-store durability (B-5, E11).

## Alternatives considered (minimum two)
| Alternative | Pros | Cons | Why not |
|---|---|---|---|
| A. One protocol, memory + SQLite, journal with digests (chosen) | standard library only; identical interface; one transaction domain gives the transactional outbox for free; restart and tamper tests run in CI in seconds | SQLite is a single-node file (no replication, no multi-writer across hosts); digests without a key are tamper-evident, not tamper-proof | Chosen for dev/sim; R-05 stays open until the Postgres adapter is evidenced on the deployed topology |
| B. Postgres + Redpanda from the compose stack now | production shape | provisioning is a human act (H-05); tests need containers; the seam would still have to be written first | Deferred: the seam is the prerequisite either way |
| C. JSONL journals per store (the revocation/nonce pattern) | already used; trivially inspectable | no transactions, no atomic multi-row writes, no read-your-writes across processes without re-reading the file; a lease needs compare-and-set | Rejected for the lease and the gateway; kept for revocations/nonces (O-55) |
| D. Pickle/JSON snapshot of the whole platform at intervals | simplest | a crash between snapshots loses the very invariants at stake; no per-row provenance | Rejected |
| E. Keep in-memory, prove durability only at Gate C on Postgres | no work now | every Gate C claim would be made without a test that can run in CI; ADR-014/015 conditions stay open | Rejected |
| Integrity: per-row digest only / chained journal only / HMAC with a process key | cheaper / stronger | row-only misses deletions; journal-only misses live edits until restart; an HMAC key must be persisted and rotated (a secret) | Both digests chosen now; keyed or anchored journal referred to the Security & Privacy Board with O-54 |

## Consequences
- Restart tests exist and run in CI: TC-DUR-001..004, TC-EX-011, TC-KS-010. Evidence stays tagged dev/sim.
- The gateway reads its indexes through the store on every access; a second executor on the same store sees one truth (TC-DUR-002). The in-process cache only avoids re-decoding an unchanged order JSON.
- One SQLite file holds Control-plane and Execution-plane state in dev/sim. In deployment each service owns its schema and its outbox; the table namespaces map one-to-one. The shared file is a dev/sim convenience, not the topology.
- The control-plane intent tracker (`oms.lifecycle.IntentTracker`) and the composition root's decision index (`decisions`) are still in memory. After a restart the permission oracle refuses every pre-restart intent as "unknown to the control plane" (fail closed, TC-EX-011): an in-flight order can be cancelled but not resumed. Resumption needs those two stores behind the same seam (O-33 / R-05 follow-up).
- The journal grows without bound (same as the nonce journal, O-55). `synchronous=FULL` costs an fsync per commit; the full suite measured 9.5 s before and 8.9 s after (177 tests, memory default): JSON encoding of orders behind the seam is not measurable at this size, so one code path costs nothing here.
- `Activation` and every event schema are unchanged (`export_event_schemas --check` green).

## Controls and tests affected (RTM rows)
FR-13 (gateway inbox, decision index, consumed grants, per-intent index), FR-17 (activation state), NFR-CON-01 (outbox relay, inbox), NFR-RES-01a (lease across failover and restart). Tests: TC-DUR-001..004, TC-EX-011, TC-KS-010; TC-RC-005 now injects its drift through `_put_order`.

# Amendment 1 — the journal head is anchored into the audit chain

**Status:** Proposed (2026-09-08) · **Amends:** §Decision item 4 and item 6 ("a keyed (HMAC) or externally anchored journal" — *not decided here*) · **Deciders:** ARB and Security & Privacy Board recommend; the Product Owner decides (D-039/D-040) · **Provenance:** [Committee: D-061 (5) Option B; Security & Privacy Board COUNCIL_2026-09-08_gate_B_spb_docs §3.1; ADR-020/D-062; REVIEW_2026-09-08_security_docs_v1.1 §10 SA-PO-2] / [Open: O-54, O-128, O-133, O-110] · Register item B-1, delegation D-051. Author: build agent E07 (AI). Reviewer: pending (Security Architect, Integration Architect). Approver: pending. This amendment is written with the commit that introduced the mechanism; it does not approve it.

**Why an amendment and not a new ADR.** The original text of this ADR states the residual in its own alternatives table ("digests without a key are tamper-evident, not tamper-proof") and its item 6 defers exactly this choice by name. D-061 (5) closed that deferral. A third ADR would leave a reader of ADR-018 believing the store's integrity story is what §Decision item 4 says it is; an amendment in the same file is where an auditor following T-61 will look. The audit half already has its own ADR (ADR-020) and is unchanged by this.

## Decision
1. **The head.** `Store` publishes `journal_head(at=None) -> JournalHead(store_id, sequence, digest)`: the sequence and chained digest of the last journal entry (or of the entry at `at`), and nothing else — no row value, no key, no secret. `MemoryStore` returns `None`: an in-process store has no file an offline actor could rewrite.
2. **The store identity is configured, not read out of the file** (`SqliteStore(store_id=...)`, defaulting to the file stem), so that swapping in a different or empty file cannot also swap the identity and make a rollback look like a store that was never witnessed.
3. **Anchoring.** `rtcore.journal_anchor.JournalAnchor` writes the head into the audit chain as a typed audit row `store.journal.anchored` carrying `{store_id, sequence, head_digest, trigger, tables}` under the correlation id of the transaction that moved it. The audit chain then covers that row with its own `payload_hash`/`hash`/`prev_hash` and, once sealed, with the external anchor written by a different principal (ADR-020).
4. **Cadence, configurable, dev/sim defaults only.** A head is anchored (a) on **every committed transaction that touches a control invariant** — `killswitch.activations`, `execution.consumed_authorisations`, `execution.by_decision`, `execution.leases`, and `__sequence` keys prefixed `fencing:` (the list the Board named, §3.1); (b) every `anchor_every` journal entries otherwise; (c) at **open**; and (d) **on demand** for an operator or a monitor. `anchor_every = 25` and `max_lag = 200` are placeholders in the shape ADR-020 already uses, not decided values [Open: O-133]. Anchoring happens **after** the control-store COMMIT: recording before it would witness heads that never existed, so every crash would look like tampering.
5. **The check, fail closed.** `verify()` at open, before anything reads or writes the store, refuses it with `StoreIntegrityError` and raises the catalogued S1 `store.journal_unwitnessed` when the witnessed head is later than the store's own (`STORE-JOURNAL-ROLLBACK`), disagrees at a sequence the chain does record (`STORE-JOURNAL-FORK`), is absent for a non-empty journal (`STORE-JOURNAL-UNWITNESSED`), or is staler than `max_lag` (`STORE-JOURNAL-STALE`). An empty journal with no witness is genesis, anchored at sequence 0, so "no anchor" is never read as "nothing has happened yet". The alert's auto-action is **none** on purpose: a Kill Switch activation is a store row, and reacting by writing to the store under investigation would destroy the evidence.
6. **The composition, on demand.** `verify(with_witness=True)` additionally asks the witness whether *it* verifies against its own external anchor (`STORE-JOURNAL-WITNESS-UNTRUSTED`). It is a separate call because ADR-020, not this ADR, owns what a failing audit chain does to a running platform.
7. **Direction of dependency.** `rtcore.journal_anchor` declares a three-method `JournalWitness` protocol (record one typed row, read typed rows back, self-report) and imports no service. `audit_service.journal_witness.AuditJournalWitness` implements it over `AuditStore.append` — the append path that already existed and the only one there is — and never sees a `Store`, a path or a digest algorithm. The audit service therefore holds no copy of the control store's internals, and the control plane gains no audit write path it did not already have. No AI/MCP component can reach either side.
8. **Incidents are durable.** A refusal writes exactly one `store.journal.incident` row; the next successful verification writes `store.journal.recovered` under the **same correlation id**. The "one incident open" state is read back out of the chain, not held in memory, so it survives the restart that a refusal causes.

## Alternatives considered (minimum two)
| Alternative | Pros | Cons | Why not |
|---|---|---|---|
| A. Keyed HMAC over rows and journal, vault-held key | defeats an actor with file write access who does not hold the key | a secret to custody, rotate and re-key inside the Execution plane, where `secrets_mount: none`; useless against an actor who can read the process, and the verifier must hold it | Rejected by the Board (§3.1) and not adopted |
| **B. Anchor the head into the audit chain (chosen)** | no new secret; defeats consistent rewrite, rollback and silent restore of a stale backup; survives the change from SQLite to Postgres; gives one chain of custody journal head → audit row → audit head → off-box anchor | does nothing the audit store is not durable and externally witnessed for; leaves the window since the last anchor; costs one audit append per control commit | Chosen (D-061 (5)) |
| C. OS-level immutability and permissions | trivial; catches accidental edits by other services | nothing against a privileged actor; does not exist once the store is a Postgres database | Mandatory hygiene alongside, not evidential, and not implemented here [Open: O-128] |
| D. Anchor only at open and at shutdown | cheapest | the whole running window is unwitnessed; a crash loses the shutdown anchor precisely when it matters | Rejected |
| E. Anchor on every commit without exception | smallest window | one audit append per sequence bump, including outbox rows that carry no control invariant | Rejected: the trigger set is the Board's list, widening it is the owner's decision [Open: O-128] |
| Placement: `SqliteStore` calls the audit service directly / a third component above both / the chosen protocol-plus-adapter | fewer moving parts | would make `libs/core` import a service, or would put audit row formats in the composition root | Chosen form keeps one direction and one seam |

## Consequences
- **T-61 changes.** The row's "the consistent rewrite is not attempted" is now attempted, in TC-DUR-007, and refused. The residual is no longer "tamper-evident against inconsistent edits only"; it is "tamper-evident unless the attacker also holds the anchor principal's write credential", which in dev/sim is a directory on the same host [Open: O-54].
- **O-54 and O-133 become load-bearing for the control store too**, exactly as SA-PO-2 said they would. Before shadow, the anchor principal must be a real second identity and the cadence a decided value.
- **A lost or unverifiable audit trail now blocks the control store from opening** when the head cannot be checked. That is intended and it is a new way to stop a deployment: the runbook must say restore-then-verify, never disable the check [Open: O-134].
- **Cost, measured in dev/sim on this machine:** one `run_intent` on a SQLite platform went from 28.3 ms to 30.1 ms (median of 7) and wrote 3 anchored rows instead of 0; platform open and restart were unchanged within noise (63–70 ms). The witness lookup at open is a linear scan of the audit chain: 9.0 ms over 20 000 events, against the 1 082 ms the audit store already spends loading and verifying that same chain (ADR-020). Start-up therefore stays O(events) with a slightly larger constant, and compaction is owed with the rest (O-55/O-111).
- **Two directories must be restored together.** A backup of the control store that predates the witnessed head is refused: the DR plan must restore control store, audit store and anchor replica to consistent points.
- No event schema changed (`export_event_schemas --check` green). `MemoryStore` platforms are byte-for-byte unchanged: no anchor object, no anchored rows.

## Controls and tests affected (RTM rows)
NFR-CON-01 (durable control state and its integrity), NFR-AUD-01 (the audit chain as the witness), NFR-RES-01a (a refused store never trades). Tests: **TC-DUR-005 (positive), TC-DUR-006 (negative), TC-DUR-007 (abuse), TC-DUR-008 (recovery)**; TC-AUD-006..009 unchanged and still green; the shared attacker helper `_rollback_consistently` was strengthened to re-create rows that the truncated tail had deleted, which makes the modelled attacker stronger, never weaker.
