## Context
Every MCP server must refuse to start with an unsigned or tampered registry. No production key exists yet (MISSING_ACTIONS: vault/KMS provisioning is human).

## Decision
`mcp_servers.registry` verifies an HMAC-SHA256 over the canonical JSON of the registry with the key from `RT_MCP_REGISTRY_KEY`. A public dev key is embedded for the sim environment and is refused by `scripts/verify_tool_registry.py --production`. Emergency revocation is a runtime flag (`revoke_registry`) plus rotation of the key.

## Alternatives considered
| Alternative | Pros | Cons | Why not |
|---|---|---|---|
| HMAC with KMS key (chosen for now) | simple, fast, testable | symmetric: verifier holds the key; rotation needs redeploy | acceptable until Gate B; asymmetric planned |
| Ed25519 signatures, public key in image | verifiers hold no secret; offline verification | key ceremony and tooling needed | target for Gate B/D once KMS exists [Open: O-22] |
| Sigstore/cosign on the registry artefact | transparency log | infrastructure dependency | evaluate with artefact signing (SECURITY_PLAN) |

## Consequences
The dev key is a known, documented non-secret (security/secret_scan_allowlist.txt). Production deployment is blocked by CI until the KMS key is configured.

## Controls and tests affected
FR-09, NFR-SEC-01; TC-AI-005 (unsigned/tampered refused), contract test on `--production` refusal.
