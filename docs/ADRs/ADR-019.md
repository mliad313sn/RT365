# ADR-019 — Asymmetric signing with a public trust set: verify-only handles and overlap-then-retire rotation

**Status:** Accepted for dev/sim with conditions (D-060, 2026-09-08; conditions (a) the pure-Python Ed25519 is dev/sim material and is benchmarked or replaced before shadow — O-125; (b) the trust set is carried by the deployment runbook, CODEOWNERS and the installer before shadow — O-126; (c) the committed registry stays dev-signed until the key ceremony exists — O-127, H-20; (d) key custody at start-up stays inside the O-53 pack; (e) protected-path approvals are Gate C conditions). **The decision-log entry is the truth; this line quotes it and does not create it** [Source: 13, CLAUDE.md] · **Date:** 2026-09-08 · **Deciders (ARB, Security & Privacy Board):** ARB, Security & Privacy Board · **Consulted:** Security Architect, MCP Security Agent, Backend Lead, Trading Domain Lead, SRE Lead · **Provenance:** [Source: 04 tool registry, 06 secure SDLC] / [Committee: D-053 (O-22), ADR-011, ADR-015, IVA-22 (R-44), REVALIDATION V-C2] / [Open: O-53 key custody, H-20 ceremony, O-23 artefact signing]

Author: build agent E13 (AI), completed by the Product Owner delegate · Reviewer: pending (Security Architect, MCP Security Agent) · Approver: pending (ARB and Security & Privacy Board recommend; the Product Owner decides, D-039/D-040). Register item B-4, delegation D-051.

## Context

Two signature checks gate the control envelope, and until now both were symmetric.

The **tool registry** (`mcp/policies/tool_registry.signed.json`) was HMAC-SHA256 under a key read from `RT_MCP_REGISTRY_KEY`, with a public dev key compiled into `mcp_servers/registry.py`. Every verifier — MCP servers, `rt365 check`, the installers — therefore had to hold the key that signs. Whoever can verify can forge.

The **order-command authorisation** (ADR-015, added after IVA finding V-C2) was an in-process HMAC held by the composition root. IVA-22 (R-44) then found that `verify_command=authoriser.verify` exposed `sign` through `__self__`, which was remediated by a verify-only `CommandVerifier` wrapper — a wrapper around the same secret, not a different key.

D-053 (2026-09-08) decided the target: an Ed25519 (or ECDSA P-256 where a KMS lacks Ed25519) key pair per purpose with a public trust set, the dev HMAC key retired outside dev/sim. This ADR records how that is built and what the dev/sim implementation does and does not prove.

A constraint shaped the implementation: `cryptography` is not in the declared dependency closure (`pyproject.toml`, `requirements.lock.txt`), and the rule for this delivery is not to add a runtime dependency for a control this small. RFC 8032 is short, its test vectors are public, and verification uses public inputs only.

## Decision

1. **One key pair per purpose, never shared.** `rt365.tool-registry.v1` and `rt365.order-command.v1` today; `risk-policy` reserved (R-29). Every signature binds purpose and `key_id` into the signed bytes (`signed_message(purpose, key_id, message)`), so a registry signature can never pass as a command grant.
2. **Verifiers hold public material only.** `rtcore.trust` carries Ed25519 verification and `TrustSet` (public keys by `key_id`, with `valid_from`, `valid_until`, `revoked`, and a ceremony reference). `rtcore.signing` carries the private-key operation and is imported only by composition roots and signing jobs; TC-AI-005 bans it from `mcp_servers`.
3. **Verify-only handles at the boundary.** The execution gateway receives a `PublicKeyCommandVerifier` (no `sign`, no private bytes, nothing reachable by attribute walk); the registry loader receives a `TrustSet`. This closes R-44 by construction rather than by wrapper.
4. **Algorithm allowlist before any curve operation.** `Ed25519` through the trust set; `HMAC-SHA256` only when `RT_ENV` is dev or sim. An envelope claiming an algorithm it was not signed with is refused, in both directions.
5. **Rotation is overlap-then-retire.** Add the successor to the trust set (both verify), re-point the signer, then `retire()` the predecessor — which sets `revoked` and makes it verify nothing whatever the timestamps say. A `key_id` is never reused.
6. **Validity is checked at the moment the artefact claims to have been authorised**, not at wall-clock now: the gateway checks the key window at `command.authorised_at` (itself bounded to `COMMAND_MAX_AGE` around now), so a clock skew cannot resurrect a key.
7. **Dev/sim keeps the HMAC paths, explicitly.** `build_sim_platform` uses the in-process HMAC authoriser unless a `command_signer` is passed, and the committed registry stays HMAC under `key_id: dev-key-v0` marked `dev_key_in_use`, refused outside dev/sim from any source. No existing dev/sim outcome changes.
8. **The production private key is never in the repository.** It is generated non-exportable in a KMS/HSM under the ceremony in `security/signing/ceremonies/TEMPLATE.md` (three distinct humans; the Product Owner may witness but holds no sign or export grant); only the public half and the ceremony record are committed, under 2nd-line CODEOWNER review.

## Alternatives considered

- **Add `cryptography` (or PyNaCl) and use its Ed25519.** Faster, constant-time, audited. Rejected for now: it adds a compiled runtime dependency to the declared closure and to every frozen executable for a verification path that handles public inputs only. To be revisited when the KMS client library arrives anyway (a KMS signer needs an SDK); the seam is `rtcore.signing`, so the swap touches one module. [Open: O-22]
- **Keep HMAC and protect the key better (vault, per-service keys).** Rejected: the verifier population is large and includes installers and the CLI on operator machines; a symmetric key that every verifier holds is a forging key by definition.
- **X.509 certificates and a CA.** Rejected as disproportionate: a handful of long-lived keys with an explicit trust file is auditable by reading one JSON file; a CA adds chain validation, revocation transport and an expiry failure mode without adding a control this delivery needs.
- **Sign only the registry, leave commands symmetric.** Rejected: the command grant is the control that stands between a decision record and a broker route; it is the one most worth forging.
- **Detached signature files instead of an envelope field.** Rejected: a detached file is easy to lose in packaging, and the envelope already travels with the artefact.

## Consequences

- The gateway and the registry loader can no longer produce a signature, and a code path that tries is a type error rather than a review finding.
- Rotation becomes an operational routine with an evidence trail (ceremony record, trust-set commit, AEI row) instead of an environment-variable change.
- The pure-Python Ed25519 is roughly two orders of magnitude slower than a native implementation. Measured effect on the suite: none worth reporting at dev/sim volumes (207 tests in ~17 s). Before shadow, either the KMS signer or a native verifier must be measured against NFR-PERF budgets. [Open: O-125]
- The trust set is now a file that must be present, correct and reviewed. An absent trust set is an empty trust set and refuses everything (fail closed) — which is safe but is also a new way to break a deployment; the deployment runbook must carry it.
- Key custody at start-up (who hands the composition root its signer, how it rotates) remains O-53. Nothing in this ADR persists a private key.
- ECDSA P-256 is not implemented. If a target KMS lacks Ed25519, `ALGORITHMS` and the verifier gain one branch. [Open: Q-22-1]
