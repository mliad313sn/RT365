# ADR-014 — Per-intent live-order invariant and broker-query-before-resubmit
**Status:** Proposed · **Date:** 2026-09-07 · **Deciders (ARB):** ARB (contracts, ADR-003 revision), Trading Risk Committee · **Consulted:** Trading Domain Lead, Integration Architect, Broker-Connector Lead, Backend Lead · **Provenance:** [Source: 00, 03, 05] / [Committee: REVIEW_C2 OBJ-1, OBJ-2, §5] / [Open: O-26 ADR-003 rev.2, O-27 adapter contract, O-28 lease policy, R-05 durability]

Author: Delivery Orchestrator (AI) · Reviewer: pending (committee) · Approver: pending (ARB). Written after remediation commit `09a6e716` to record the mechanism that commit introduced; it does not approve it and does not amend ADR-003.

## Context
ADR-003 derives `idempotency_key = hash(intent_id, account, policy_version)` and states that an intent re-evaluated under a new policy version "becomes a new key by design". The Execution Gateway deduplicated on that key only. REVIEW_C2 OBJ-1 (global R-02 re-rated Critical, T-26) reproduced two live broker orders for one `intent_id` with a clean reconciliation by re-issuing the command under a second `policy_version` — no failover required. REVIEW_C2 OBJ-2 (R-09, T-27) reproduced the ambiguous-failure path: after a lost acknowledgement, `retry_submit` re-sent under the same `client_order_id` and relied on a broker capability (`dedupes_client_order_id`) that ADR-002 says cannot be assumed and that the gateway never read; on a non-deduping broker this produced two live orders, and on the never-received branch the SUBMITTED order could be neither cancelled nor expired nor reconciled.

## Decision
1. **At most one live broker order per `intent_id`, enforced in the Execution plane.** The gateway keeps an `intent_id → [order_id]` index. `submit()` first applies the idempotency-key inbox (unchanged), then refuses any command whose intent already has an order in an open state or with filled quantity (`DuplicateIntentOrder`, a `ControlDenied`), audits `order.command.duplicate_intent_rejected` and raises S1 `execution.duplicate_order` (auto-action `killswitch_account`). `policy_version` no longer changes the number of live orders an intent can have (`services/execution/execution_gateway/gateway.py`).
2. **Broker query before any resubmit.** The adapter contract gains `query_order(client_order_id, now) -> OrderStatus` (`connectors/brokers/broker_adapters/base.py`; implemented by the simulated broker). `retry_submit` queries first and adopts the broker's state — OPEN/PARTIAL/FILLED → ACKNOWLEDGED, CANCELLED → CANCELLED, otherwise BROKER_REJECTED — and only re-sends when the broker reports the id as unknown. `cancel()` of a SUBMITTED order also queries first and, if the broker never saw it, cancels locally with reason "never reached broker". `sync_statuses` adopts broker-side terminal states (IOC cancel, post-ack reject) and `expire_unacked` expires SUBMITTED orders whose intent expiry passed once the broker confirms it never saw them.
3. **State machines admit the outcomes above.** Order machine: SUBMITTED → CANCELLED/EXPIRED, ACKNOWLEDGED → EXPIRED. Reconciliation groups live orders by `intent_id` and raises DUPLICATE S1 when more than one exists, and STATUS S1 when internal and broker states disagree (ADR-014 companion decision D-017).
4. **Not decided here.** Whether ADR-003's key should drop `policy_version` (reviewer's option B) is O-26 for the ARB; a cancel/replace path with its own key derivation and a REPLACED state is O-33; lease TTL/heartbeat and an authorised `preempt` are O-28; the durability of the intent index is R-05.

## Alternatives considered (minimum two)
| Alternative | Pros | Cons | Why not |
|---|---|---|---|
| A. Keep the ADR-003 key; add the gateway per-intent invariant (chosen) | Exactly-once business effect enforced at the last component with a broker route; no broker dependence; failover semantics unchanged | New index must be durable (R-05); policy re-evaluation of a live intent becomes an explicit two-step (cancel, then new command) | Chosen as defence in depth |
| B. Change ADR-003: key = hash(intent_id, account); `policy_version` an attribute | One key per intent for life; cannot create a second order by construction; simplest | Loses "re-execute under a new policy"; needs an explicit replace key derivation | Recommended by the reviewer as the ADR-003 amendment; referred to the ARB as O-26 (not decided in this cycle) |
| C. Broker-side dedupe on an intent-derived client id | Uses venue dedupe | Only where `dedupes_client_order_id` is true — the assumption ADR-002 rejects | Rejected |
| D. Status quo plus RK-DUP window | No change | In-memory Control-plane state; reproduced failure | Rejected |
| Resubmit alternatives: rely on `dedupes_client_order_id`; resubmit under lease only; park as UNRESOLVED with S1 | Fewer adapter methods | The first repeats the rejected assumption; the second still duplicates on a non-deduping broker; the third leaves capital in an unknown state | Query-first chosen; parking remains the fallback when `query_order` itself raises `BrokerUnavailable` (the order stays SUBMITTED) |

## Consequences
- Every broker adapter must implement `query_order`; certification (O-32) must exercise resubmission in both dedupe modes and the status mapping (O-27 enum).
- A legitimate re-evaluation under a new policy must cancel the live order first; the Control plane needs an explicit supersede path (O-33).
- The invariant is only as durable as the gateway's index (R-05); until a durable store exists the evidence is tagged dev/sim in the RTM.
- An in-memory `_by_intent` entry survives only for the process lifetime; TC-EX-011 (restart redelivery) remains a Gate D test to write.
