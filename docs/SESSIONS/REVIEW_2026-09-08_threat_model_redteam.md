## 1. Verdict

**SIGN WITH FINDINGS.**

In plain terms: the document is honest about what it does not have, and that is rare enough to be worth saying first — I checked all 88 rows, and every row that names a test which does not exist says so. I am signing it as an accurate dev/sim baseline. But it is not yet accurate everywhere, and two of the inaccuracies are the kind that makes a reader think a control is running when it is not. **Blocking (the reviewer column of AUDIT_EVIDENCE_INDEX row 2 should not be filled until these two rows are corrected by their author):** (RT-F1) row T-13 claims an egress allowlist as a delivered control, and the allowlist object is loaded at start-up and then never consulted by any code that makes an outbound call — the test cited calls the checker directly, so it proves the file parses, not that anything is filtered; (RT-F2) the audit rows T-12, T-16, T-76 and T-77 say the platform "fails closed" against the external witness, and it does not fail closed by itself — I truncated the audit trail, restarted the platform, and it started, ran an intent and sent an order to the broker; the witness is consulted only when a human opens the console or runs the CLI, and when the witness is simply deleted the alert that fires carries no automatic action at all. **Non-blocking but important:** the model has no row for four attacks that I ran successfully or that its own new data flows imply — substituting the trust anchor the signature scheme is checked against (I forged a tool registry with my own key in a minute), starting the platform against an empty state directory (which silently discards an engaged Kill Switch and every audit record, with everything then verifying clean), the unsigned per-tenant allowlist files, and denial of service *against* the fail-closed controls themselves. None of that stops Gate B, which authorises dev/sim only and where the residual is accepted (D-058 b); all of it must be answered before shadow. Finally, a wording constraint the Board already set holds: with 26 rows carrying an [Open] test marker, **no gate report, board minute or external statement may say the threat model is covered by tests** (O-143) — and the count in O-143 says twenty, which is wrong (§3, RT-F11).

## 8. Control quartets for the two controls that changed this week

Written by the reviewer as the shape a retest would take; **the author of a quartet is not its approver, and the builder allocates the ids.**

**Control A — the audit witness comparison as a platform behaviour (the gap behind RT-F2/RT-F3).**
- *Positive*: a platform opens on an intact chain whose witness matches; the comparison runs at open and on the schedule; the platform serves and one audit row records the successful verification.
- *Negative*: the chain is shorter than the witness, or the heads differ → the platform refuses to serve the trading path (or takes the catalogued action the Trading Risk Committee confirms under O-137) **without a caller having to ask**; the S1 alert names the reason code.
- *Abuse*: the witness is deleted, and the deletion is then "repaired" by an operator seal → the seal is refused because the chain is shorter than the store's own last seal record; a stale backup is restored → refused; the anchor tail is removed together with the seal rows → still refused.
- *Recovery*: the witness replica is restored from the last good copy, verification passes, and the incident and its recovery are audit rows sharing one correlation id (the shape TC-AUD-009 already proves).

**Control B — trust-anchor integrity (the gap behind RT-F6 / T-89).**
- *Positive*: a registry signed by a key in the reviewed trust set loads; the trust set's own fingerprint matches the value the binary or the deployment carries.
- *Negative*: the trust set is absent or malformed → nothing asymmetric loads (already true today).
- *Abuse*: a trust set containing an attacker's key, or a bundle containing both a forged registry and a matching trust set → refused because the trust set does not match the pinned fingerprint; a retired key restored by editing the file → refused.
- *Recovery*: a genuine key rotation replaces the trust set through the ceremony, the fingerprint is updated in one reviewed place, and the old key is refused absolutely from that moment.

## 10. Concerns for the Product Owner

- **RT-PO-1 I am signing the threat model, and the signature is narrower than it looks.** [Verified] My signature says: the document describes the dev/sim state honestly, its [Open] tags are real (I checked all 88 rows mechanically), and it is a sound basis for planning. Both are one-paragraph edits by the author, not new engineering. **Decide:** ask for a v1.1a with those two rows and hold the evidence-index row until it exists.
- **RT-PO-2 The audit trail's witness is a witness only when somebody looks.** [Verified: probe 01] I truncated the audit trail, restarted the platform and it traded — one order reached the broker — because the comparison against the external witness happens when `verify()` is called (a console endpoint, a health probe, the CLI), not when the platform opens. Deleting the evidence is currently a better attack than editing it. **Decide:** treat "the witness comparison is wired to a platform behaviour, and the response to a witness failure is a decision the Trading Risk Committee has taken (O-137)" as a shadow entry condition, and note that the anchor cadence and staleness ceiling (O-133) become load-bearing at the same moment.
- **RT-PO-3 The recovery step for a lost witness destroys the evidence it is meant to protect.** [Verified: probe 01 C] With the witness gone, the single action available to an operator — seal — re-anchors whatever chain is present, and the platform then reports healthy. A genuine replica loss and a deliberate truncation look identical to the operator, and the runbook that would tell them apart does not exist (O-134, whose text also asserts, incorrectly, that a lost witness stops the platform). **Decide:** make O-134 a control gap rather than a documentation gap, and do not let the runbook be written by the same seat that owns the control.
- **RT-PO-4 The residual you already accepted is bigger than the words suggest — and I have now measured it.** [Verified: probe 03] T-61 honestly says a consistent rewrite of the store is undetectable.
