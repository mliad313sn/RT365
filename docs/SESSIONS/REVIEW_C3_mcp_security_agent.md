## 2. Purpose

- AI/MCP may research, analyse, simulate, rank, signal and submit typed trade intents only; never broker credentials, limit changes, self-approval, audit suppression, monitoring disablement or control bypass. **[Source: 00, 04]**
- Six allowed capabilities; forbidden list (direct broker calls, arbitrary code execution, shell, secret retrieval, risk-policy mutation, audit deletion, unrestricted web access, dynamic installation). **[Source: 04]**
- C3 design decisions 1–6: signed tool catalogue with scope/masking/quota/timeout/payload/class/owner/approval; forbidden = structurally impossible; short-lived signed identity; provenance labelling, delimited untrusted text, schema-validated outputs, canary strings; model lifecycle; explainability contract. **[Committee: COMMITTEE_DEEP_DIVE.md §C3]**
- Threat rows T-01 (injection), T-02 (excessive agency), T-08 (replay), T-12 (audit tampering), T-13 (exfiltration). **[Source: 06]** with test IDs TC-AI-002/003/004, TC-NET-003. **[Committee: THREAT_MODEL.md]**
- This challenge asks whether the implementation as wired (not only the `mcp_servers` package in isolation) makes the forbidden capabilities structurally impossible, and whether the evidence (TC-AI-001..005, TC-NET-001..004) proves what the catalog claims. **[Committee]**
- Model provider, hosting and eval-dataset terms remain unspecified (O-05, O-06); no LLM is wired in the dev/sim build, so "agent" in this review means any holder of an `AgentIdentity` token. **[Open]**

## 3. Three strongest objections

### OBJ-1 — `run_simulation` is an agent-callable path that disables the S1 plane-deny alert and destroys deny evidence on the live platform (forbidden capability: monitoring disablement / audit suppression)

- **Severity:** Critical (Gate B and D blocker; blocks registration of `run_simulation`).
- **Where:** `apps/web/web_bff/platform.py:710-716` (`run_sim` handler) → `:738-747` (`run_sim_backtest` calls `build_sim_platform(...)`) → `:394-396` (`guard = GUARD; guard.denies.clear(); guard.alert_hook = lambda ev: alerts.raise_alert(...)` where `alerts` is the *throwaway* simulation's `AlertRouter`). `GUARD` is the process-global singleton in `libs/core/rtcore/planes.py:82`.
- **Reproduced (read-only probe):**
  ```
  run_simulation ok: True ... GUARD.alert_hook identical before/after: False
  live platform plane.deny alerts after crossing: 0     (fresh platform control: 1)
  denies before: 1  ->  denies after run_simulation: 0
  ```
- **Impact:** Any identity granted `run_simulation` (the default `strat-sma-xover` grant in `mcp/policies/allowlist.tenant-sim.yaml`) can, with one allowed call, (a) re-point the global plane guard's alert hook to an object nobody observes, so every later Analytics→Execution route attempt on the live platform raises **no** `plane.deny` S1 alert and triggers **no** `revoke_agent_identity` auto-action (`observability/alerts.yaml:5`), and (b) wipe `PlaneGuard.denies`, the in-process evidence used by TC-NET-002. This is exactly the "disable monitoring / suppress audit" capability blueprint 00 forbids, reachable through an *allowed* tool. It also breaks the TC-NET-002 abuse quartet's premise: the test passes only because no `run_simulation` call precedes it.
- **Secondary defects in the same handler:** (i) the handler ignores `template`, `strategy_id`, `strategy_version` (probe: bogus strategy and version → `ok: True`), so "approved simulation templates" (`tool_registry.json` scope) is not enforced by code; (ii) every call constructs a full platform including an `ExecutionGateway` and a `SimulatedBroker` and runs the pipeline to a broker adapter in the analytics-plane process — the ADR-008 single-code-path decision puts execution-plane classes into MCP handler memory, which TC-AI-005's import scan does not see because the handler lives in `apps/web/web_bff/platform.py`, not in `mcp_servers/`; (iii) resource bounds are only `quota_per_minute: 6` per tenant and a *post-hoc* 60 s timeout; no CPU/memory ceiling, no queue (catalog says "queued").
- **Remedy (owner: Backend Lead; reviewer: MCP Security Agent; verifier: IVA):**
  1. `build_sim_platform` must never touch the global `GUARD` (inject a `PlaneGuard` instance; the composition root for backtests must use a private guard) — or `run_sim_backtest` must run in a separate process/worker with no shared state.
  2. Handler must validate `template ∈ approved templates`, resolve `strategy_id@strategy_version` from the registry with status ≥ VALIDATED, and refuse otherwise (`ToolDenied("SCOPE")`).
  3. Add TC-AI-006 (abuse): call `run_simulation`, then attempt an Analytics→Execution crossing; assert `plane.deny` S1 fires and `guard.denies` is non-empty.
  4. Threat-model delta for ADR-008 vs ADR-001: document why execution-plane code in the analytics process is acceptable, or move the backtest runner behind a queue in its own namespace with no broker adapter classes loaded.

### OBJ-2 — The registry trust root is a public symmetric key with silent fallback; a forged registry adding `cancel_order` is accepted

- **Severity:** Critical (Gate B blocker; contradicts "unsigned server is refused at startup").
- **Where:** `mcp/servers/mcp_servers/registry.py:16` (`DEV_KEY` literal), `:52-56` (`signing_key()` falls back to `DEV_KEY` when `RT_MCP_REGISTRY_KEY` is unset), `:73-75` (verification uses the same key); `scripts/sign_tool_registry.py:21-22`; `scripts/verify_tool_registry.py:16,23-24` (`--production` is opt-in); `Makefile` `policy-check` and `.github/workflows/ci.yml` run verification **without** `--production`; `infra/docker-compose.yml` sets `RT_MCP_REGISTRY_KEY: ${RT_MCP_REGISTRY_KEY:-}` (empty → dev key).
- **Reproduced:**
  ```
  RT_ENV=production, RT_MCP_REGISTRY_KEY unset -> loaded with dev key: True, env tag: sim
  re-sign tool_registry.json + {cancel_order, class: write} with DEV_KEY -> forged registry accepted: True
  scripts/verify_tool_registry.py            -> OK (dev key)     [what CI runs]
  scripts/verify_tool_registry.py --production -> FAIL            [nobody runs this]
  ```
- **Impact:** If `RT_MCP_REGISTRY_KEY` is unset in any environment the runtime *silently* trusts the key printed in the source tree. Anyone with repository read access can produce a validly signed registry containing any tool. HMAC is symmetric, so every MCP server that can *verify* can also *sign*; a compromised analytics pod can re-sign its own registry. `key_id`, `algorithm` and `environment_tag` are outside the signed content and never checked (`registry.py:70-75, 99`), so a `sim` registry loads in production and key confusion is undetectable. `test_tc_ai_mcp.py::TC-AI-005` "unsigned registry refused" therefore proves only that an *unsigned* file is refused, not that an *unauthorised* one is. Finally, the signed registry carries `approval_record: "[Committee: pending]"` for all six tools — it was signed before review, by the builder's tooling, which violates "author ≠ reviewer ≠ approver" (blueprint 13) for the very artefact whose signature is supposed to embody approval.
- **Remedy (owner: Backend Lead for code; MCP Security Agent for key custody; Security Architect review):**
  1. Fail closed: `load_registry` refuses the dev key unless `RT_ENV in {dev, sim}` **and** an explicit `RT_ALLOW_DEV_REGISTRY_KEY=1`; production path with no key → `RegistryUnsigned` at startup.
  2. Move to asymmetric signatures (Ed25519 via KMS/HSM). Servers hold only the public key; signing happens in the MCP Security Agent's CI job. Include `key_id`, `algorithm`, `environment_tag`, `registry_version` and `signed_at` in the signed payload; verify `environment_tag == RT_ENV`.
  3. CI runs `verify_tool_registry.py --production` on release branches; `docker-compose` and Helm values must not default the key to empty.
  4. A registry with any `approval_record` still "pending" must not be signable (`sign_tool_registry.py` refuses); approval records must reference a DECISION_LOG entry.
  5. Note: `scripts/secret_scan.py` reported "0 files" on this branch (no commits, so `git ls-files` is empty) — the T-05 gate that should have flagged the committed key was a no-op. Owner: Security Architect.

### OBJ-3 — Revocation and alert auto-actions do not behave as the catalog states: a low-privilege agent revokes `submit_trade_intent` tenant-wide, three S1 auto-actions are no-ops, and a restart silently un-revokes everything

- **Severity:** High (Gate D blocker; makes the "emergency revocation" control unevidenced).
- **Where:** `apps/web/web_bff/platform.py:699-707` (`revoke_agent_identity` reads `payload["agent"]`; `revoke_tool_for_tenant` revokes for the whole tenant on any `mcp.non_allowlisted_tool`); `mcp/servers/mcp_servers/runtime.py:104-108` (NOT_ALLOWLISTED raises that alert); `mcp/servers/mcp_servers/allowlist.py:26-30` (no grant/restore method); `identity.py:32-34`, `runtime.py:57-59` (all revocation state in process memory); `services/killswitch/killswitch_service/service.py:73,123` and `libs/core/rtcore/planes.py` deny hook (payload keys `actor`/`source`, never `agent`); `test/quartets/test_tc_ai_mcp.py:84-88` (asserts the tenant-wide revocation as intended behaviour).
- **Reproduced:**
  ```
  research agent (strat-research-only) calls submit_trade_intent -> NOT_ALLOWLISTED
  trading agent (strat-sma-xover) afterwards -> NOT_ALLOWLISTED          # tenant-wide DoS by a read-only agent
  allowlist methods: ['allowed','load','revoke_tool','tenant_id']         # no restore path
  killswitch.agent_attempt payload keys: ['actor','level','target'] -> revoked agents: {'unknown'}; agent still usable: True
  plane.deny payload keys: ['source','destination','channel'] -> revoked agents: {'unknown'}
  200 NOT_ALLOWLISTED probes -> 200 S2 alerts, 200 pager deliveries (no quota consumed)
  revoke_tool + revoke_registry, then rebuild platform -> read_market_snapshot ok: True
  ```
- **Impact:** (a) Any identity in the tenant — including one whose only grant is research reads, or one obtained by injection — can switch off intent submission for every strategy and account of the tenant (a "control bypass" of availability; for a live account this is an un-audited trading halt with no two-person restore). (b) The S1 responses for Analytics→Execution attempts, agent Kill-Switch attempts and RK-INTEG violations revoke the literal agent `"unknown"`; the catalog's "revoke agent identity" auto-action is fiction in three of four cases. (c) Because NOT_ALLOWLISTED is checked before the quota, an agent can flood pager/email without limit. (d) Every revocation (tool, registry flag, agent, scope, allowlist edit) lives only in process memory: a pod restart or HPA scale-out silently restores all revoked capabilities, and `mcp/policies/README.md` "revoke registry signature → all servers refuse at next call" is not what the code does (the code flips a boolean on one `ToolRuntime`; rotating the key would refuse *at startup* on the next restart, the opposite semantics). No drill artefact exists.
- **Remedy (owner: Backend Lead; SRE Lead for alert wiring; MCP Security Agent specifies):**
  1. Scope `revoke_tool_for_tenant` to the offending `(tenant, account, strategy)` and require the payload to carry them; tenant-wide revocation is a human, two-person action.
  2. Alert payload contract: every alert whose auto-action is `revoke_agent_identity` must carry `agent`; `AlertRouter` must refuse to bind an auto-action when the payload lacks the required key and must raise an S1 `alert.autoaction_failed`.
  3. Rate-limit denials per identity (deny bucket) and per tenant; count denied calls against quota.
  4. Persist revocations (revocation list keyed by `token_id`/`agent_id`/`tool`, replicated via the Control→Analytics `revocation` channel) and make servers fetch the revocation head at startup; define "revoke registry signature" as key rotation + push of a revocation record, and run the drill (H-19 family) with a logged artefact.
  5. Add TC-AI-007 (abuse): research agent NOT_ALLOWLISTED must not affect the trading agent; TC-AI-008 (recovery): revocation survives runtime restart.

## 9. Verdict

- **Tool registration (the six entries in `tool_registry.signed.json`): REJECT** as currently signed. Signature predates approval; `run_simulation` cannot be registered until OBJ-1 is closed; `submit_trade_intent` cannot be registered until F-01 (replay) and F-07 (`strategy_version`) are closed; `read_account_state` cannot be registered until O-22 (masking policy) exists. The four read tools' *specs* are acceptable in principle once F-07/F-10/F-13 remedies are in the spec.
- **Gate B (architecture): ACCEPT WITH CONDITIONS** — conditions: OBJ-1 remedy A merged with TC-AI-006; OBJ-2 items 1, 3, 4 (fail-closed key, CI `--production`, no signing while pending) and O-23 decided; F-19 policy fix plus effective-union checker; O-21 answered with a threat-model delta. Independent Validation retains veto.
- **Gate D (supervised pilot): REJECT at this time.** Beyond the Gate B conditions, D requires OBJ-1 option B or C, OBJ-3 remedies 1–5 with a logged revocation drill, F-01, F-04 (principal separation), F-05, F-12/F-13 (corpus and applied provenance labelling), and second-line-signed evidence for every TC-AI/TC-NET quartet (F-22).
- **What is sound and should be kept [Committee]:** registry refuses handlers not in the signed registry; write-class is limited to the intent queue and the intent queue enforces the plane check and strict schema; identity check binds account/strategy on submit; output size and canary checks run before output schema; MCP audit rows enter the hash chain; `check_caller` fails closed for unattributed callers; `--production` verification logic exists and works (it simply is not wired).
- **Confidence:** High on OBJ-1, OBJ-2, OBJ-3, F-01–F-08, F-13, F-19 (each reproduced by probe or by direct code reading with line citations). Medium on F-05 (event-loop blocking reasoned from code, not load-tested), F-17/F-18 (resource behaviour with real data not measured), A-06 (CNI behaviour not verified on a cluster). Low on anything concerning a real model or real broker — none exists in this build [Open: O-05, H-07].
