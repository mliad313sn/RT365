### 6.1 Registry environment-label binding (the MSA-F-1 remedy) — owner: build-e09; reviewer: MCP Security Agent; before O-127 closes
- **Positive.** `RT_ENV=sim`, a registry tagged `sim`, correctly signed → loads; `rt365 check --env sim` reports the environment it bound.
- **Negative.** `RT_ENV` **unset**, a validly Ed25519-signed non-fixture registry tagged `sim` → **refused** with a reason that names the missing label. The current behaviour loads it; this is the case that does not exist today.
- **Abuse.** `RT_ENV` unset, a validly signed registry tagged `production` → refused (probe P-1 result A is the counter-example this must eliminate). `RT_ENV` set to an empty string → refused. `RT_ENV=dev` with a `sim` tag → still allowed, the one documented widening, and the test must pin it so it is not widened further by accident.
- **Recovery.** With the label restored, the same file loads and the platform serves; the refusal and the recovery share one correlation id in the audit chain.
- **Residual after the control exists.** Whoever sets `RT_ENV` decides the environment; the label is an assertion by the deployment, not a proof. That is why the environment tag is inside the signed envelope and why the trust set is per purpose — but it remains true, and no gate record should say the ladder is cryptographically enforced [Open: H-05].

### 6.2 Emergency revocation drill (T-7 above; my mandate, blueprint 04) — owner: SRE Lead (runs it, H-19); Product Owner (names the operators); reviewer: MCP Security Agent (semantics), IVA (record)
- **Positive.** A named operator revokes the registry version; the next tool call on every runtime sharing the revocation list returns `REGISTRY_REVOKED`; two **distinct** named approvers restore it; calls resume. Recorded with times and names.
- **Negative.** One approver, or the same name twice, cannot restore (`ControlDenied`: "registry restore requires two distinct approvers"); a revoked tool stays revoked across a restart.
- **Abuse.** A line is deleted from `revocations.jsonl` between the revocation and the restart, and the target silently un-revokes — **this is the case the drill must attempt and expect to fail**, because the journal has no digest and no chain (O-55, O-118, O-128). The drill record must state that it failed and why, or the drill is theatre. Once the journals move onto the Store seam (D-061 (6)) the same case must then pass.
- **Recovery.** After the deletion is detected, the revocation is re-issued, the incident and its recovery are audit rows sharing one correlation id, and the runbook step that pairs the control store with its journals as one restore unit is exercised (O-118, O-136).
- **Residual.** In dev/sim both stores sit on one host under one principal; the drill proves the human procedure and the code path, not the tamper-evidence, which waits on O-128.
