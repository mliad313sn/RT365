## 2. Purpose

Two things, both in the same few lines of the composition root.

**(a) Defect F-02.** The two integrity checks that protect this platform run *inside* the constructors that open the stores: `SqliteStore.__init__` replays the control journal (ADR-018 §Decision 4) and `AuditStore.__init__` verifies the audit chain (ADR-020 §Decision 2). The composition root built both, and only then called `alerts = AlertRouter.load(...)` and `audit.set_alert_sink(alerts.raise_alert)`. So at the moment of either failure `self._alerts is None` and no router existed at all: **no catalogued S1, no auto-action, nothing delivered, nothing on a dashboard**. What an operator got was a service that did not come back. ADR-020's own rule 5 says a verification failure "raise[s] the catalogued S1 alert"; for the open-time path that sentence was not true of the running system. In the SRE Lead's words, "fail closed" was accurate and "fail closed and you will be told" was not (PO-S1, SRE-R1) [Committee].

**(b) Decision D-066 (O-164).** Composition compared the control store's journal head against the audit chain — cheap, and blind to an attacker who rewrites *both* stores consistently, which is exactly the attack TC-DUR-007 (d) carries out. That attacker is caught only by the anchor a different principal published, and nothing asked for it until the next scheduled publication, an explicit `/v1/audit/verify` or `rt365 check`. The Product Owner decided that composition must call the published verification at start-up, following ADR-020's existing path on failure (alert, auto-action, platform Kill Switch) rather than refusing to compose [Source: DECISION_LOG D-066].

**What this is not.** It enables no market, no strategy and no autonomy; it moves nothing along the environment ladder; it removes, relaxes and skips no verification; it adds no flag that could disable one (O-165 stands); and it gives no AI or MCP component a new path — the router, the store opens and the start-up verdict are composition-root code, and the one MCP tool that builds a platform (`run_sim` → `run_sim_backtest`) passes a fixed argument list with no router and no store directory [Committee].

## 3. Decisions taken in this session (≥ 2 alternatives each) — proposed to `docs/DECISION_LOG.md`, **not written by me**

**ADR-020 amendment 2** is the artefact of record and I wrote it into `docs/ADRs/ADR-020.md` (proposed; reviewer pending). Its eight decision points and six alternatives are there in full. The build-level choices behind them:

| # | Choice | Alternatives weighed | Why this one |
|---|---|---|---|
| B-1 | **Load the router first; open each store with the sink in place; announce, then re-raise unchanged** | (i) catch and continue with a degraded platform; (ii) leave the order and write to stderr with a distinct exit code; (iii) a separate bootstrap sink object with its own severities | (i) is fail-open on the two controls that must never fail open. (ii) is not an alert: no severity, no auto-action, no delivery, and the catalogue would still describe a control that does not fire. (iii) is how two systems come to disagree about what an alert means. The chosen shape is the smallest change that makes ADR-020 rule 5 true |
| B-2 | **`SqliteStore(path, verify=False)` then an explicit `store.verify()` in the composition root** | keep `verify=True` and catch the exception out of the constructor | Catching out of the constructor leaves a live SQLite connection with no owner on the failure path. The explicit form moves the *same* check one line, changes no ordering (the constructor already did DDL before verifying), closes the handle, and leaves `verify=True` the default for every other caller. **No verification is skipped**: TC-AUD-012 and TC-AUD-014 prove the refusal still happens |
| B-3 | **Reuse `execution.store_unavailable` and `audit.chain_verification_failed`; add no new alert name** | add `store.open_refused` to `observability/alerts.yaml` | I may not write `docs/ALERT_CATALOG.md` (§7). A name in the YAML without its catalogue row makes the two files disagree, and the SRE Lead's own rule is that the catalogue is the source of truth for what an alert does. I propose the catalogue wording to him instead (§7) and use the two names whose severity and auto-action already fit |
| B-4 | **Two reason codes: `STORE-OPEN-REFUSED` (integrity) and `STORE-OPEN-UNAVAILABLE` (availability)** | one code for "the store would not open" | RB-13 turns on this distinction — "the two classes have opposite recoveries" — and an operator who cannot tell them apart from the page will guess. TC-AUD-012 asserts both |
| B-5 | **One `startup:<id>` correlation id per composition attempt, stamped on every start-up alert including the audit chain's own** | let each component mint its own | Two alerts from one failed boot are one incident. `AuditStore.verify(correlation_id=...)` takes the caller's id; an already-open anchor incident still keeps its own, so an incident is never split (ADR-020's "exactly one incident row" is unchanged) |
| B-6 | **Let `alert.autoaction_failed` fire when `killswitch_platform` is unbound at open** | bind a no-op (or a "record the intent" stub) to `killswitch_platform` during bootstrap | Binding anything would report a halt that did not happen. `alert.autoaction_failed` exists precisely so a silent no-op is impossible, and the process refusing to start is a **stronger** stop than the Kill Switch it could not reach. Asserted in TC-AUD-011 |
| B-7 | **Run D-066's published verification after the auto-actions are bound, and do not refuse to compose** | run it inside `AuditStore.__init__`; or run it early in composition and raise | Inside the constructor a missing witness — catalogued auto-action **`none`** — would become an unconditional outage, which is the opposite of what the catalogue says. Raising early would leave nothing able to run the Kill Switch the failure calls for. D-066 chose the alert path; TC-AUD-013 shows the halt actually engaging |
| B-8 | **Expose the start-up verdict on `/v1/audit/verify` and `/v1/status`** | keep it in-process only | DR review D-03: "the process starting is evidence of the first check and is **not** evidence of the second". A reader must be able to tell "verified at boot and passed" from "nobody asked until you did". `None` means no external witness is configured, so "not checked" is never displayed as "checked and fine" |

## 6. Finding F-01 — the corrected behaviour, as row text for the Cloud Architect (I did not edit `docs/CAPACITY_MODEL.md`)

The SRE Lead is right that the document merges two failures with two behaviours, and right about what the two alert files say. **I re-checked the code against both files at this commit: `observability/alerts.yaml` and `docs/ALERT_CATALOG.md` agree with each other and with the code on every audit and store alert** — `audit.anchor_missing` S1 / `auto_action: none`, `audit.chain_verification_failed` S1 / `killswitch_platform`, `store.journal_unwitnessed` S1 / `none`, `execution.store_unavailable` S1 / `none` — and I introduced no new alert name, precisely so they stay in agreement (§3 B-3). One thing F-01 says has **changed** with this commit and the row must say so: the witness *is* now checked at start-up.

**Proposed replacement for CAPACITY_MODEL §1 (audit store row), §4 (row 4) and §4a (row 6)** — four paths, not one, each with its catalogued auto-action [Committee]:

| At start-up | What is checked | Reason codes | Catalogued alert / auto-action | What actually happens |
|---|---|---|---|---|
| Control store opens | journal replay against the state (ADR-018) | `STORE-OPEN-REFUSED` / `STORE-OPEN-UNAVAILABLE` | `execution.store_unavailable`, S1, auto-action **none** | The process **refuses to start**; the S1 is now raised and delivered before the exception propagates (was silent — F-02) |
| Audit store opens | the audit chain's own hashes (ADR-020) | `AUD-CHAIN-BROKEN` (or `STORE-OPEN-REFUSED` at the seam) | `audit.chain_verification_failed`, S1, auto-action `killswitch_platform` | The process **refuses to start**. The S1 is now raised and delivered (was silent). The auto-action **cannot run** — there is no platform yet — and the router says so with `alert.autoaction_failed` (S1). The stop is the process not starting, not a Kill Switch |
| Journal head vs the audit chain | ADR-018 amendment 1 | `STORE-JOURNAL-*` | `store.journal_unwitnessed`, S1, auto-action **none** | The process **refuses to start**; deliberately no automatic halt, because a Kill Switch activation is itself a control-store row |
| **New (D-066):** the chain vs the **published** witness | ADR-020 amendment 2 | `AUD-ANCHOR-MISSING` / `-STALE` / `-CHAIN-BROKEN` / `-TAIL-REMOVED` **→ no halt**; `AUD-CHAIN-TRUNCATED` / `-HEAD-MISMATCH` **→ halt** | `audit.anchor_missing` S1 / **none**, or `audit.chain_verification_failed` S1 / `killswitch_platform` | The platform **starts either way**. A missing, stale or corrupt *witness* pages a human and trading continues (the chain may be intact). A chain that **contradicts** the witness starts the platform **halted**, platform-wide |

Three consequences for the document, none of which needs a number: (1) "a missing witness halts the platform via `killswitch_platform`" is wrong in both directions and should be split as above; (2) "largest blast radius" belongs to `audit.chain_verification_failed`, and only in the case where a platform *exists* to halt — at open it is a refusal to start, and in a multi-cell deployment it stops one cell, not the platform; (3) §4a should now carry a **third** O(n) start-up cost: the published-anchor read (`FileAnchorPublisher._read()` re-verifies the whole anchor file) now runs once at every durable start-up as well as on the append path (F-04), so start-up is O(events) in the two stores **plus** O(anchors). The platform-halt semantics remain [Open: O-137] — a proposal awaiting the Trading Risk Committee, not a decided value.

**F-02's §4a row** can also be retired in its "detection is the absence of a healthy process" form and replaced by: *the start-up verifications fail closed **and** now emit their catalogued S1 with a start-up correlation id before the process exits; detection is an alert, with the residual that the alert path terminates in-process (SRE-R5) and that a process killed before composition still tells nobody.*

## 7. Text I propose for `docs/ALERT_CATALOG.md` (owned by the SRE Lead; the write-scope guard does not carry it and I did not route around it)

Two edits, both wording. Neither changes a severity or an auto-action, and the YAML needs no change if they are taken as written — which is the point.

1. **`execution.store_unavailable`, condition column.** Currently "StoreError (unreadable or corrupt control store) **at submit, retry or cancel**; the gateway submits nothing and fails closed". Proposed: "StoreError or StoreIntegrityError on the control store **at open, submit, retry or cancel**; at open the platform refuses to start and the payload carries `STORE-OPEN-REFUSED` (integrity — treat as a suspected tampering incident, RB-13) or `STORE-OPEN-UNAVAILABLE` (availability — an environment fault); at submit, retry or cancel the gateway submits nothing. Auto-action stays **none**: an automatic write to a store under investigation would destroy the evidence [Committee: ADR-020 amendment 2, BUILD_E11 F-02]".
2. **`Audit chain verification fail`, auto-action column.** Currently "halt trading; forensic". Proposed: "`killswitch_platform` when a platform exists to halt; **at open there is none**, so the platform refuses to start and the router raises `alert.autoaction_failed` (S1) naming the unbound action — the operator is told both that the chain failed and that the automatic halt did not run [Committee: ADR-020 amendment 2]".

**If the SRE Lead would rather have a name of its own** for "a store would not open" (his SRE-R6 pattern for the trust set), I would support `store.open_refused`, S1, auto-action **none**, runbook "store unavailable" — but it must land in the catalogue and the YAML on the same commit, and that commit is his, not mine.

## 11. Concerns for the Product Owner

- **PO-1 The two worst failures now page, and I want you to know exactly how far "page" goes.** Before this change, when either integrity check refused a store, nothing at all was emitted: no alert, no automatic action, nothing on a dashboard — the only sign was a service that did not come back. That is fixed in the sense the SRE Lead asked for: the alerting path is now built before any store is opened, both failures raise their catalogued S1 with a correlation id, and I have a test that corrupts a store file on purpose and proves the alert is delivered rather than merely requested. But "delivered" today means delivered to two lists inside the same process that is about to exit. There is no pager, no email, no external notifier, no timestamp on delivery and no acknowledgement anywhere in this platform (the SRE Lead's SRE-R4 and SRE-R5, which are his to close). I have built the seam a real notifier plugs into, and a deployment can now hand the platform an alert path that already reaches a human before the platform exists. Until something is plugged into it, the honest sentence is: **"fail closed, and the system now tries to tell you"** — not "and you will be told" [Committee].

- **PO-2 What an operator still would not be told, in plain terms.** Four things, and I would rather write them down than have someone meet them at 03:00. (i) If the process is killed *before* it composes — out of memory while loading a long audit trail, or an orchestrator start-up timeout — nothing is emitted, because nothing got far enough to emit it; the SRE Lead's health-check-based page remains the only detector for that case, and the memory limit that would bound it does not exist anywhere (O-160). (ii) If the alert catalogue file itself is missing or malformed, the platform fails closed *before* the router exists and emits nothing at all — the same shape as the missing trust set, one level further out; I have proposed a deployment-time presence-and-hash check rather than inventing a fallback catalogue, because a made-up catalogue would be worse than silence. (iii) The alert that fires when the audit chain is refused at open names an automatic platform halt that **cannot run**, because there is no platform yet; the system says so out loud with a second S1 rather than pretending, and in a multi-cell deployment a refused cell stops itself and does not stop its siblings. (iv) An alert delivered inside a process that then exits can be lost in the same instant, and nothing would show that it was lost. None of these is introduced by this change; all four were true before and remained invisible [Committee].

- **PO-3 The witness is now checked when the platform starts, and that changes what a bad recovery feels like.** You decided (D-066) that composition must ask the external witness — the independent record of how long the audit trail is — rather than waiting for the next scheduled check. It does, and the test that matters shows an attacker who rewrites *both* the control store and the whole audit trail so they agree with each other being caught at start-up by the one record he does not own, with the platform-wide Kill Switch engaged before a single decision is taken. The consequence to be deliberate about: the SRE Lead's PO-S2 error — bringing up a standby with an audit trail *shorter* than the witness — now halts that platform at start-up rather than some minutes later. That is the right time to learn it, and it makes his ordered restore instruction (restore the audit store, check its length against the witness, then attach the witness, then verify, then seal) a prerequisite rather than an improvement. It is the Cloud Architect's document, and it is not in it yet [Committee; Open: D-01 in his review].

- **PO-4 Start-up now reads three long things instead of two, and none of them is measured.** Every start-up on durable storage replays the control journal, loads and verifies the whole audit chain, and — new with D-066 — reads and re-verifies the whole external anchor file. All three grow with how much history the platform has, and none has ever been measured. I have added no number and I will not estimate one; I have put it in the register as an input to the measurement the SRE Lead has already sequenced. The reason it matters to you rather than only to engineers: recovery time is how long these three take, and the parameter that controls how often the trail is witnessed is now a divisor of a start-up cost as well as a security setting — so the security board and the capacity work must still decide it together (his F-04, O-133) [Open: O-156, O-18].

- **PO-5 One thing got noisier on purpose, and one thing I could not do from this seat.** Noisier: a platform whose external witness is missing now records an incident in its audit trail every time it starts, each under that start-up's own identifier, instead of once. Every one of those is true — each start really did find the witness missing — but it is not the single tidy incident the design describes, and it makes the runbook line "do not restart to clear it" load-bearing rather than advisory. Could not do: the alert catalogue is the SRE Lead's document and I may not write it, so I reused two alerts that already exist rather than inventing a name that would have appeared in the machine-readable file and not in the human one. I have written the two wording changes I would like him to make, and I did not route around the guard to make them myself [Source: 13].

- **PO-6 Nothing here is approved, including by me.** I wrote the tests first and watched all five fail before I wrote a line of the fix. I changed no existing test: the 220 that passed before still pass unchanged, including the one that models the adversary this change catches earlier, so nothing was weakened to make anything green. I removed no check, relaxed none, and added no way to switch one off. I amended an ADR and it says **Proposed**; its reviewers are the SRE Lead, whose finding this is, and the Security Architect, and both are pending. I edited no register: every row above is proposed for the Program Orchestrator. My second line is the Compliance Agent and the independent validation is a third seat — and the adversary in my new tests is my own, so it must not be described as independent evidence [Source: 13; Committee: the O-144 rule].
