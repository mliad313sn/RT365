## 3. Three strongest objections

### OBJ-1 — Critical — Nothing enforces "one live broker order per intent"; ADR-003 makes a second one legitimate and reconciliation cannot see it

**Where.** `libs/core/rtcore/schemas/order.py:23-30` (key = hash(intent_id, account, policy_version); client_order_id derived from key); `docs/ADRs/ADR-003.md:8,14` ("Intent re-evaluated under a new policy version becomes a new key by design"); `services/execution/execution_gateway/gateway.py:100-142` (dedupe only on `idempotency_key`, line 103; no lookup by `intent_id`); `services/reconciliation/reconciliation_service/reconcile.py:116-140` (DUPLICATE is raised only for a broker order with no internal counterpart, line 125, or two client ids sharing one broker ref, line 120).

**What happens.** **[Probe P1]** Submit a resting LIMIT intent; hand the gateway a second `OrderCommand` for the *same* `intent_id` with `policy_version` "v0.2" (the situation ADR-003 calls "by design", e.g. a policy rollout with redelivery of `eligibility.decided`, or a risk-service replay). Result: `same intent_id: True | distinct order ids: True | distinct client_order_ids: True | broker submissions: 2 | open orders: 2 | reconciliation clean: True`. Two live orders for one intent, each with an internal counterpart, so the DUPLICATE classifier is silent and no ticket, no Supervised, no Kill Switch.

**Why the upstream defences do not close it.** The pipeline inbox (`oms/pipeline.py:89-91`) is keyed by `intent_hash`, the intent tracker (`oms/lifecycle.py:88`) is monotonic, and the risk engine has RK-DUP over the last 500 intent hashes — but all three are in-memory Control-plane state (`Inbox` at `oms/outbox.py:36-43`, `IntentTracker` at `oms/lifecycle.py:76-92`, `AccountBook.recent_intent_hashes` in `portfolio_service/ledger.py`) that a restart or a second consumer instance empties. The Execution Gateway is the one component with a broker route [Source: 00] and it holds no per-intent invariant. ADR-003 alternatives (a)/(b) were rejected for creating duplicates; alternative (c) as written also creates them whenever `policy_version` moves, which C4 maker-checker makes a routine event.

**Impact.** Exactly-once *business* effect (NFR-CON-01) is not delivered — only exactly-once per (intent, policy) tuple. Duplicate orders (R-02) are possible without any failover at all. Broker-as-truth is undermined because the truth is checked by client_order_id, which the duplicate legitimately owns.

**Remedy.** (i) ARB decision on ADR-003: either drop `policy_version` from the key (re-evaluation under a new policy of an intent that already produced an order is *not* a new order — P1 already says "any change is a new intent") or keep it and add the gateway invariant below; (ii) Execution Gateway keeps a durable `intent_id → order_id` index and rejects/parks (`order.command.superseded`, alert S1) any command whose intent already has a non-terminal order, unless the command carries an explicit `supersedes_order_id` (cancel/replace path, which does not exist today — see F-06); (iii) reconciliation adds an intent-level check: >1 broker order per `intent_id` (join statement ↔ internal by coid, group by intent) → DUPLICATE S1; (iv) quartet TC-EX-007/008 (§6). See §5 for the alternatives comparison.

### OBJ-2 — Critical — The SUBMITTED-but-unacked path is unsafe on both branches: retry assumes broker dedupe that ADR-002 says cannot be assumed, and the orphan can never be cancelled, expired or reconciled

**Where.** `gateway.py:159-165` (BrokerUnavailable → "Leave SUBMITTED: a retry with the same key is deduped; reconciliation confirms broker state"); `gateway.py:178-193` `retry_submit` docstring "same client_order_id, so the broker dedupes"; `connectors/brokers/broker_adapters/base.py:28` `dedupes_client_order_id` declared but **never read** by the gateway (grep: only `base.py` and `simulated.py` reference it); `gateway.py:19-29` order machine: SUBMITTED → {ACKNOWLEDGED, BROKER_REJECTED, PARTIALLY_FILLED, FILLED} — **no CANCELLED, no EXPIRED**; `reconcile.py:148` TIMING check covers ACKNOWLEDGED/PARTIALLY_FILLED/FILLED only — SUBMITTED is invisible; `base.py:110-141` `BrokerAdapter` has **no order-status query** (no `get_order(client_order_id)`), so the ambiguous failure cannot be resolved except by waiting for a statement.

**What happens.**
- **[Probe P2b]** Broker accepted the order but the ack was lost (adapter raises after the broker recorded it), broker configured `dedupe_client_order_id=False` (a capability ADR-002 explicitly allows): `retry_submit` → broker holds **2 OPEN orders** under `coid#1`, `coid#2`; the statement collapses both under one client_order_id so `reconcile()` is **clean**; `cancel()` returns UNKNOWN_ORDER so the account-level **Kill Switch cancels nothing** (`KS cancelled: ()`), both orders stay live. With `dedupe=True` [P2a] the path works — the guarantee therefore rests entirely on a broker capability the design says is optional.
- **[Probe P3]** Broker never received it (`fail_submissions=True`): order stays SUBMITTED; Kill Switch → `cancel()` gets UNKNOWN_ORDER, state stays SUBMITTED, still counted in `open_orders` (feeds RK-RATE-OPEN and open-order notional forever); 24 h later `reconcile()` is clean; intent stuck in SUBMITTED; `SUBMITTED→CANCELLED: False, SUBMITTED→EXPIRED: False, PARTIALLY_FILLED→EXPIRED: False`. Nothing in the platform ever calls `retry_submit` (only the test does), so in the delivered wiring the orphan is permanent.
- The certification harness makes this worse: TC-BR-004 (`certification.py:199-202`) **requires** `a2.status == DUPLICATE`, so a non-deduping broker can never be certified, silently contradicting ADR-002(b) while the gateway silently depends on dedupe.

**Impact.** Duplicate live orders (R-02) on the most common real-world failure (timeout after send) with a certified-but-non-deduping broker; and an un-cancellable, un-reconcilable open order on the other branch — the Kill Switch's "cancel open orders" [Source: 05] is not guaranteed. S-03 in docs/SEQUENCE_DIAGRAMS.md:44-45 promises "reconciliation confirms single broker order"; the code cannot.

**Remedy.** (i) Adapter contract gains `query_order(client_order_id) -> BrokerOrderStatus | None` (capability-discovered) and the gateway's ambiguous-failure protocol becomes: query → if known, adopt broker state; if unknown and `dedupes_client_order_id` is false, only resubmit under a lease *and* after `query` returns None twice across a configurable window, else park as `UNRESOLVED` and alert S1; (ii) add SUBMITTED → CANCELLED (local cancel of a never-sent order, audited as `order.cancelled.v1` with reason `NEVER_ACKED`) and SUBMITTED/ACKNOWLEDGED/PARTIALLY_FILLED → EXPIRED driven by TIF/DAY session end and by a `submit_timeout`; (iii) reconciliation treats SUBMITTED older than the timeout as a TIMING break (S2) and a SUBMITTED order that appears on the statement as a status break; (iv) a scheduled re-driver in the execution plane (not the test) for SUBMITTED orders; (v) harness: run TC-BR-004 in both capability modes and record which one the broker exhibits.

### OBJ-3 — High — Reconciliation compares quantities only, never order status or fees; "broker statement is final truth" is therefore true for positions and false for order state, cash and cancels

**Where.** `reconcile.py:116-140` (order loop compares `filled_quantity` only; `StatementOrder.status` at `base.py:94` is a free string that is never read); `reconcile.py:159` (cash tolerance 0.01 absolute, no fee/accrual model; `ledger.py:87` fee parameter exists but `apps/web/web_bff/platform.py:241-251` `settle()` never passes it); `tickets.py:33,56-70` (two-person rule with no different-line requirement; resolution does not require a subsequent clean run); `reconcile.py:74` break_id includes wall-clock seconds so every cycle mints a new ticket for the same break.

**What happens.**
- **[Probe P6]** Internal CANCELLED, broker OPEN (cancel not honoured / raced with fill): `reconcile clean: True`. After a Kill Switch this is exactly the case that matters — orders believed cancelled are live and nobody is told.
- **[Probe P6]** IOC limit far from market: broker CANCELLED at once (`simulated.py:170-171`), gateway ACKNOWLEDGED, `open internally: 1`, reconcile clean. The internal open-order count drifts upward for every IOC/DAY expiry; no event, no break.
- **[Probe P11]** Paper fills carry `fee applied: 0.000000`; a real statement carries commissions, so live cash will break by the fee amount on every fill (S2 → Supervised each cycle), or the operator widens `cash_tolerance` until it is useless. Backtest deducts fees outside the pipeline (F-14) so the backtest ledger would break against its own sim broker if reconciled.
- **[Probe P12]** Same break across two cycles → 2 open tickets; OPS + SRE (both 1st line) resolve; `RESOLVED` while `break still present: True`; account still SUPERVISED with no path back defined.

**Impact.** The Gate C entry criterion "no open reconciliation breaks" [Source: 12] can be met on paper while real state diverges; the P6 promise "resolution with two-person confirmation" is weaker than the Kill Switch two-person rule (which does enforce different lines, `killswitch_service/service.py:136-139`).

**Remedy.** Add `BreakType.STATUS` (internal terminal/open vs broker open/terminal, S1 when internal CANCELLED/none and broker live); reconcile SUBMITTED (see OBJ-2); model expected fees/accruals per broker in the cash comparison with a per-currency tolerance owned by TRC [Open]; make ticket identity `(account, break_type, instrument|coid)` so recurring breaks update one ticket; require the second resolver to sit in a different line (reuse `Actor.line`); require a clean reconciliation run after resolution before autonomy can be restored; publish `reconciliation.break.v1`/`completed.v1` on the outbox (today audit-only, F-19).

## 9. Verdict, confidence, provenance

**Verdict for Gate C (paper readiness) on C2 / P1 / P6 / E03 / E07: REJECT — re-submit after conditions.**

The delivered code is a strong dev/sim skeleton: plane guard, fencing, deterministic key derivation, monotonic machines, break tickets and the certification harness all exist and the quartets are green. But the two guarantees Gate C exists to certify — exactly-once business effect and broker-as-truth reconciliation — are demonstrably not held by the Execution plane on its own: one intent can become two live orders with a clean reconciliation (OBJ-1); the ambiguous-failure path either duplicates or orphans (OBJ-2); and the reconciliation cannot see a cancel that the broker did not honour (OBJ-3). "Open reconciliation breaks" is an IVA veto ground at Gate C; breaks that *cannot be detected* are worse than open ones.

Conditions to move to ACCEPT WITH CONDITIONS (in order of dependency):
1. ARB decides O-20 and records ADR-003 rev.2; gateway per-intent invariant + reconciliation intent-level DUPLICATE (OBJ-1 remedies i–iii) with TC-EX-007/TC-RC-008 green.
2. Adapter `query_order` + ambiguous-failure protocol + SUBMITTED→CANCELLED/EXPIRED + SUBMITTED re-driver; TC-EX-009/010, TC-BR-008 green; certification harness run in both dedupe modes (OBJ-2).
3. STATUS break type, SUBMITTED coverage, fee-aware cash, ticket dedupe, different-line resolver, RECONCILED transition (OBJ-3, F-13, F-16); TC-RC-005..009 green.
4. Kill Switch cancel scope and lease preemption scoped per level (F-01); TC-KS-007 green.
5. `order.command.v1` producer/schema fixed and emitted-event validation in CI (F-29); EVENT_CATALOG/OpenAPI parity (F-30/31) — Integration Architect to author, Backend Lead to review, ARB to approve.
6. Costs inside the ledger for BACKTEST and PAPER (F-25); RTM re-tagged so that in-memory evidence is labelled "dev" and NFR-CON-01 durability moves to Gate D (F-09/R-08).
Items F-02/F-03/F-04/F-07/F-11/F-12/F-21/F-27 should be scheduled before Gate D at the latest; F-12 (tracker reset) is cheap and should ride with condition 1.
