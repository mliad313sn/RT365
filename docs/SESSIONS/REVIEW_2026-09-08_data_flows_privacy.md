## 3. Verdict — **SIGN WITH FINDINGS**

**In one paragraph, for a non-specialist.** DATA_FLOWS v1.1 is a large and honest improvement on v1.0 and I am willing to sign it as the Gate B picture of where data moves in dev/sim: it draws the store, the journal, the audit file, the anchor directory and the MCP journals that v1.0 hid, it separates what is built from what is only planned, and it does not pretend that residency, retention or WORM exist. I am **not** willing to sign it as it stands, because six statements in it would mislead the people who act on it: the audit row credits a legal-hold control that is not connected to the audit trail at all (the retention service that implements it is an unwired, in-memory decision helper that never deletes anything and loses every hold on restart); two rows say "no PII" about data that is customer-identifying and therefore in scope for retention and subject rights; the user-facing row says telemetry is redacted when the redaction filter does not cover the operator identifier the same row classifies as Personal; the journal row does not say the one thing a reader most needs — that `delete()` does not erase, because the deleted value stays in the journal for ever and the integrity check would refuse the store if anyone removed it; the anchor row says the witness carries "no identifier" when each anchor record carries a caller-supplied correlation id and a publisher name to a store deliberately held outside our own systems; and the document points at docs/PRIVACY_IMPACT.md for a residency and retention map that does not cover any of the five things now sitting on disk. **Action:** the Data Architect issues a v1.2 with the six corrections in §3.1 (they are corrections of fact and wording, not new design), the Board takes the classification column with my recommendations in §4, and the Product Owner decides on v1.2 — not on v1.1. Everything else I found is non-blocking and is carried as [Open] items and proposed register rows. **Nothing here authorises anything beyond dev/sim, and no flow in this document is evidence for a deployed environment** [Committee] [Source: 00, 12].

## 5. The Board's question: **is the control-store journal (DF-11) a record?**

**My answer, in my own words: yes — the journal is a record, but not the same kind of record as the audit chain, and the difference decides what you must do with it.**

The reason is not the file it lives in; it is what it contains and what people will do with it. `journal` holds, for every mutation ever made to control state, the table, the key, the **entire value written**, the caller's `correlation_id` and a wall-clock timestamp, chained so that the sequence itself is evidence [Verified: store.py 141–196]. Order rows carry the whole `OrderCommand`; Kill Switch activations carry actor ids; the journal keeps every version of all of it, including the versions that were later deleted. That is, in substance, a complete and time-ordered account of what the platform did to a customer's account — which is what the "Trading records" row of docs/PRIVACY_IMPACT.md describes, and it is what an investigator, an auditor or a customer would in practice be shown. A store that is *described* as working state but is *used* as proof is a record, whatever its table is called [Committee].

But it is a record **by derivation, not by design**, and that distinction carries the consequences:

1. **Retention.** It inherits the retention of the records it duplicates — the longest retention of any class it contains (today: trading records) — because it cannot be kept to a shorter period than its content: there is no way to remove one entry. It does **not** get an independent retention rule of its own; a retention rule for the journal is a retention rule for the whole store's history. Until the schedule exists, D-025's fail-closed rule applies and nothing is deleted [Source: 06] [Open: O-09, O-111].
2. **Legal hold.** A hold on any enclosing scope must suppress deletion of the journal too. Today this is automatic in the crudest way — there is no deletion path — which is *safe* but not *controlled*: the day compaction is built it must consult the hold register **before** it truncates, and the hold register must be durable (PF-1). A hold that lives in a dict and disappears on restart is the first failure mode I look for in any system [Committee].
3. **Erasure.** The journal is where an erasure demand will actually bite: even if a customer's rows were removed from the `kv` table, their values would remain in the journal, and removing them would make the store refuse to open. An erasure answer that begins "we delete the row" is false as built. See §7.
4. **Subject access and rectification.** If the journal is a record, a subject-access answer built only from live `kv` rows is incomplete, and a rectification cannot be a rewrite — it must be a forward-only correction, exactly as with the audit chain. That is a defensible position, but it must be a stated one.
5. **What follows for the build** (not my decision — the Backend Lead's and the Board's): journal compaction (O-111) is no longer only a performance item, it is the retention mechanism, and the O-128 anchoring decision determines what a compacted journal can still prove. **A compaction design that does not carry the retention rule and the hold check will either make retention impossible or make evidence disappear** — the two failure directions, both avoidable if the design is done once with Privacy in the room.
6. **What I am not saying.** I am not saying that any law classifies this journal in a particular way, nor how long anything must be kept. Record classes and periods per jurisdiction are counsel's answer through H-04 (scope H-25) and the Compliance Agent's matrix; my classification is an internal handling classification only [Open: O-09, O-10].

**Recommended classification cell for DF-11:** *Confidential; **derived record** — inherits the retention class and legal-hold behaviour of the records it duplicates (today: trading records); no independent schedule; no erasure path exists* [Committee] [Open: O-09, O-111, O-135].

## 7. The append-only chain against an erasure duty

**What I would accept.**
1. That the audit chain **cannot delete**, and that this is a feature: an audit trail with a delete path is not an audit trail. I will not ask for a delete path, and I would refuse one if it were offered [Committee] [Source: 06].
2. That, where a record must be kept for a regulatory period, keeping it is the answer to an erasure request for that record, and D-025's fail-closed suppression is the right default meanwhile. **Which records those are, and for how long, is counsel's and Compliance's answer, not mine and not the platform's** [Open: O-09, O-10, H-04/H-25].
3. That a rectification against the chain is a **forward-only correction event**, never a rewrite, and that a subject-access answer may be assembled from a *view* over the chain rather than from the chain itself.
4. **Interim, for dev/sim only:** no real customer data exists, so nothing is presently at risk. That is why I can sign the document while the erasure answer is [Open] — and equally why the answer must exist **before the first environment with a real person's data**, not "before Gate D" [Committee] [Source: 12].

**What I refuse.**
1. Any claim — in a gate report, a DPIA, a customer document or a marketing statement — that the platform can honour an erasure request today. It cannot: the audit event stores the **full payload inline** and the verifier recomputes `hash_of(payload)` and compares it with `payload_hash`, so redacting or removing a payload makes the chain report "payload tampered" and the store refuses to open — and through `audit.chain_verification_failed` the catalogued auto-action is `killswitch_platform`. **An attempt at erasure today halts the platform** [Verified: audit store.py 226–242, 366–388; observability/alerts.yaml].
2. Any plan to satisfy erasure by disabling, weakening or skipping a verification. Recovery is restore-then-verify (O-134); erasure is never a reason to turn a check off.
3. Committing the audit store to a WORM medium, or fixing the anchor cadence, **before** the retention schedule exists (§6).
4. Treating `payload_hash` as a de-identification measure. It is an **unsalted SHA-256 over the payload**: for a low-entropy structured payload (an account id, a side, a quantity) the value is recoverable by enumeration. The same applies to the `target_hash` of `deny_scope` (NF-12). Hashing an identifier is not erasing it [Verified: audit store.py 226; app.py 110].

**What the usual remedies would require of the build** (design owed by the Backend Lead / Security Architect; I state the privacy requirement, not the implementation):

| Remedy | What it requires here | Why it is not free |
|---|---|---|
| **Payload minimisation** — the durable answer | The chained event keeps `seq, event_id, ts, correlation_id, tenant, account, actor, action, payload_hash, prev_hash`; the payload moves **out** of the chained record into a referenced store that can be reduced; verification checks `payload_hash` **as a reference**, and a "payload withdrawn" state must verify rather than fail | Today the payload is inside the hashed record and re-hashed at verify: this is a change to `AuditEvent`, `compute_hash` and `_verify_chain`, i.e. a versioned chain format and a migration, decided once. Note also that `tenant`, `account` and **`actor`** are in the hash preimage: even with payload removal, those identifiers can never be removed from an existing chain. Therefore **`actor` and `account` must be pseudonyms from the first write**, resolvable through a separately erasable identity map. That is the single design decision that keeps a future erasure answer possible, and it must be taken before any real personal data is written |
| **Crypto-shredding of referenced payloads** | Payloads encrypted per subject (or per tenant) with a key held where it can be destroyed, so destroying the key makes the payload unreadable while the chain still verifies over the ciphertext or its hash; plus a **key custody, escrow and destruction** procedure under two-person control, with evidence that destruction happened | It adds a key-management duty inside the Control/Execution envelope that the Board deliberately avoided for the store-integrity scheme (O-110 → O-128, "no new secret in the Execution plane"). The Board must decide whether a *privacy* key changes that reasoning; I record the tension rather than resolve it, because I do not approve security architecture. And an unsalted `payload_hash` **survives shredding** and re-derives low-entropy payloads — so the hash must become keyed or salted at the same time, or shredding does not shred |
| **Pseudonymisation at emission** — my recommended first step | Actor and account identifiers written into the chain as keyed pseudonyms under the per-tenant masking key already implemented in `tools.py`, with the map held in the identity service | Cheapest, breaks nothing, and it makes both remedies above viable later. It costs an incident-time lookup step and it makes the masking key a record-keeping asset with its own custody and destruction rules (NF-5) |

**Consequence for the Product Owner:** the erasure answer is not a policy sentence Compliance can write later; it is a **format decision about the audit chain that gets more expensive every day the chain grows**, and it must be taken before the first environment holding a real person's data — realistically at Gate C entry, not Gate D [Committee] [Open: O-135, O-09, O-10].

## 8. Platform-auditor privacy envelope (D-059, D-061 (7), Board §3.4, O-121)

The Board asked me to set this envelope **before any build**. It is written as requirements on a capability that does not exist; nothing here approves the capability, its route family or its identity design (Backend Lead / Security Architect / Board) [Committee].

**PA-0 Precondition.** No unfiltered cross-tenant read capability is built or enabled in any environment holding real personal data until (a) this envelope is accepted by the Board and the Product Owner, (b) the DPIA covering the reading jurisdiction exists (O-10), and (c) the read's own audit path is implemented and tested. In dev/sim the capability may be built and tested against fixture tenants only [Source: 12].

**PA-1 Purpose limitation.** The capability exists for exactly three purposes, named at the time of the read and recorded with it: (i) **assurance** — independent verification of controls and of chain integrity; (ii) **investigation** — a named incident, break or complaint with its reference; (iii) **legal hold or regulatory request** with its reference. Curiosity, product analytics, sales, model training, capacity work and support convenience are **not** purposes. A read without one of the three references is refused, not logged-and-allowed.

**PA-2 The read is itself an event.** Every unfiltered read emits an audit event (`audit.platform_read`) into the same append-only chain, carrying: reader principal, IdP session and claim expiry, purpose code, reference (case/hold id), the **tenant set touched**, the query predicate, the row count returned, whether payloads were revealed, and the correlation id. It is written **before** the result is returned (fail closed: if the audit write fails, the read fails). It carries `tenant = '-'` and is therefore invisible in tenant-scoped views — which is exactly why PA-8 exists.

**PA-3 Pseudonymisation by default.** The platform-auditor view returns **pseudonymised** account, actor and customer identifiers (keyed, under the per-tenant masking key, as `tools._pseudonym` already does) and **withheld payloads**, showing metadata, reason codes and hashes. Re-identification and payload reveal are a **separate, second act** requiring a purpose (ii) or (iii) reference and a second human approver from a different line, and they emit their own audit event naming the fields revealed. "Pseudonymised" here means *not directly readable*, never *anonymous*: the data remains personal data and this envelope applies to it in full.

**PA-4 Minimum necessary and time-bound.** Read-only; no export path into a general-purpose tool; queries scoped by time window and predicate, never "everything"; the IdP claim is time-bound (PIM window, R-06) and tenant-less; the capability is never attached to a tenant-bound principal, an agent identity, a header, a CLI flag or a service account. **No AI or MCP component may ever hold this claim** [Source: 00].

**PA-5 Residency.** A cross-tenant read is a **transfer question the moment two tenants have different `residency_region` values**. Until the DPIA answers it for the reading location (O-10), the view is restricted to tenants whose `residency_region` matches the reader's cell, and a read that would cross regions is **refused with a reason code**, not silently filtered. Building the capability without the region predicate is building a transfer with no control — and `residency_region` is currently read by no code (NF-10), so this is a build prerequisite, not a policy note.

**PA-6 What may never be exported under this claim, in any view, to anyone.** Secrets and key material of any kind (`VaultRef` targets, signing keys, masking keys); broker credentials; the re-identification map itself; market data beyond the tenant's entitlement (a licence question as well as a privacy one, O-12); free-text prompt or news content carrying third-party personal data; and **bulk payloads** — reveal is per record and reasoned, never per query. Anything that leaves the platform leaves as a **generated, watermarked evidence file** carrying the reader, purpose, reference, time and row count on its face, with its own retention (proposed PI-7).

**PA-7 Retention of the read record.** `audit.platform_read` events are Regulated-record class and are retained for at least the retention of what was read; they fall within §7 and inherit the erasure position taken there.

**PA-8 Transparency to the tenant.** The default position I recommend is that a tenant can learn, on request, that platform-auditor reads touching its rows occurred, with date, purpose class and reference, unless an investigation or a legal instruction suppresses that notification. **Whether notification is required, and whether suppression is lawful, is counsel's question (O-10, H-04/H-25) — I am specifying the design that keeps both answers available**, because a system that cannot tell a tenant it was read can never later be made to.

**PA-9 Refusal conditions (fail closed).** No purpose reference; expired claim; region mismatch (PA-5); audit write unavailable; reveal requested without a second approver; predicate absent. Each returns a reason code and raises an alert; none degrades silently to a filtered result.

**PA-10 Build prerequisite the Board should note.** The seam already offers unfiltered reads to any holder of a handle — `AuditStore.all()` / `export(tenant=None)` and `Store.items()` / `dump()` have no tenant predicate [Verified: audit store.py 262–273, 499–501; store.py 223–243]. The envelope must therefore be enforced in a **distinct route family above the seam**, and no platform-auditor path may be built by exposing the seam. T-83's "no unfiltered read path exists" is true of the BFF today and must be kept true by construction, not by convention.

**Quartet I would require before this capability is accepted** (ids by the QA Lead; **none exists today**): *positive* — a valid claim with purpose and reference returns pseudonymised cross-tenant rows and writes `audit.platform_read` first; *negative* — no reference, expired claim, tenant-bound principal, agent identity, or region mismatch are refused with reason codes and no rows; *abuse* — reveal without a second approver, bulk export attempt, the claim asserted in a header or `_meta`, and an audit-write failure during a read (which must fail the read); *recovery* — a read performed during an incident is reconstructable end-to-end from the chain, and the tenant transparency report (PA-8) lists it [Committee] [Open: O-121, R-06, O-10].

## 12. Concerns for the Product Owner

- **PC-P1 The document credits a privacy control that does not exist anywhere near the flow it is credited to.** DF-07 lists legal hold among the audit trail's controls. DATA_FLOWS is honest that residency enforcement does not exist, and §4 points at my file for a map that does not yet cover any of it.
