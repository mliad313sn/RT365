## 3 Decisions and the ADR text proposed

### 3.1 Amendment, not a new ADR — and why
The proposed text is **`docs/ADRs/ADR-018.md` § "Amendment 1 — the journal head is anchored into the audit chain"** (written in this branch, status **Proposed**, nothing in the original Decision section rewritten). Reasons, with the alternative not taken:

- ADR-018 §Decision item 6 defers this exact choice by name ("a keyed (HMAC) or externally anchored journal"), and its alternatives table states the residual in its own words. An auditor following T-61 arrives at ADR-018; if the answer lives in a third ADR, ADR-018 still reads as though its digests are the whole story.
- **Alternative A — a new ADR-021.** Cleaner status handling (ADR-018 is "Accepted with conditions" and an amendment complicates that). Rejected: it would split one decision across three documents (ADR-018 store, ADR-020 audit, ADR-021 join) and D-061 (5) is a *condition on ADR-018* (D-058 b), not a new standard.
- **Alternative B — amend ADR-020 instead.** Rejected: ADR-020 is about the audit trail's own integrity; the control store is the subject here, and ADR-020's decisions are unchanged by this build.
- The amendment is self-contained: status, deciders, provenance, decision (8 numbered points), six alternatives, consequences with measured cost, controls and tests, threat-model delta pointer.

### 3.2 The mechanism, in one line per point (full text in the ADR)
1. `Store.journal_head(at=None) -> JournalHead(store_id, sequence, digest)`; `MemoryStore` returns `None` (no file, nothing to anchor).
2. The store identity is **configured**, not read out of the file, so swapping in a different or empty file cannot also swap the identity.
3. The head is written into the audit chain as `store.journal.anchored` `{store_id, sequence, head_digest, trigger, tables}` under the **correlation id of the transaction that moved it**; the chain covers it with `payload_hash`/`hash`/`prev_hash`, and the external anchor covers it once sealed.
4. **Cadence** (configurable, dev/sim defaults, no invented threshold): every commit touching a control invariant table, every `anchor_every` entries, at open, and on demand.
5. **The check** at open, before anything reads or writes the store: `STORE-JOURNAL-ROLLBACK`, `-FORK`, `-UNWITNESSED`, `-STALE` → `StoreIntegrityError` + catalogued S1.
6. **The composition** on demand: `verify(with_witness=True)` also asks whether the witness verifies against *its* anchor (`STORE-JOURNAL-WITNESS-UNTRUSTED`).
7. **Direction of dependency** (§3.3).
8. Incidents are durable: one `store.journal.incident` row, closed by `store.journal.recovered` under the same correlation id.

### 3.3 The direction of dependency I chose, and why
**Core library → nothing; audit service → core library; composition root wires them.**

`libs/core/rtcore/journal_anchor.py` declares `JournalWitness`, a three-method protocol — *record one typed row, read typed rows back, say whether you verify* — and imports no service. `services/audit/audit_service/journal_witness.py` implements it over `AuditStore.append`, **the append path that already existed and the only one there is**, plus `by_action` for reads and `verify()` for the self-report. It never receives a `Store`, a path, a file name or a digest function, and it cannot compute a journal head; the vocabulary it will accept is a frozen set of three actions and anything else is refused (`UnknownWitnessAction`), so the anchoring path cannot be used to append arbitrary audit rows.

Consequences of that direction, stated so a reviewer can check them:
- the **audit service does not import the control store's internals** — it imports two value types (`JournalHead` is not even one of them; only `WitnessRow` and three action constants) from the core library, exactly as it already imports `Store` and `SEQUENCE_TABLE`;
- the **control plane gains no new audit write path**: `AuditStore` is unchanged by this session (zero lines), and there is still no update, no delete and no re-sequencing anywhere;
- no AI/MCP component gains anything: neither module is reachable from any registered tool, neither holds a broker route, a secret, a limit write path, an audit delete path or a mode change. The MCP tool registry, policies and schemas are untouched (`export_event_schemas --check` and `verify_tool_registry` green).

The alternatives: (a) `SqliteStore` calling the audit service directly — rejected, `libs/core` would import a service; (b) putting the adapter in the composition root — rejected, every future composition would re-implement the audit row format; (c) an event bus between them — rejected as disproportionate and because a lost message is exactly the failure this control must not have.

### 3.4 Ordering, and why anchoring is best-effort while verification is not
Heads are recorded **after** the control-store `COMMIT`, outside the transaction. Recording before it would witness heads that never committed, so every crash would look like tampering; recording after means the store may be *ahead* of the witness, which is the benign direction and is bounded by `max_lag`. A witness that cannot be written is therefore an S1 alert and a widening lag that `check()` will refuse — never a lost or rolled-back control write. **Verification fails closed** and refuses the store. This is the same discipline ADR-020 applies to its own scheduled publication, applied in the same direction.

### 3.5 Why the S1 alert has no auto-action
`store.journal_unwitnessed` is S1 with `auto_action: none`. A Kill Switch activation **is a control-store row**: an automatic halt on this alert would write to the very store whose integrity is in question, on top of a journal that may be an attacker's, and destroy the evidence. The fail-closed behaviour is the refusal itself — the platform does not start. Alternative considered: `killswitch_platform`, as `audit.chain_verification_failed` uses; rejected for that reason, and because at the point the check runs the Kill Switch service does not yet exist.

## 10 Concerns for the Product Owner

- **PC-1 The composition is enforced on demand, not at start-up, and that is a real gap I chose not to close unilaterally.** [Verified: `JournalAnchor.check_witness`, TC-DUR-007 (d)] The full property — *a head is only witnessed if the witness is itself witnessed* — is implemented and tested, but the composition root calls the cheap head comparison at open and **not** `verify(with_witness=True)`. So an attacker who rewrites both stores consistently is caught by `rt365 check`, by the next scheduled audit publication, and by any explicit verification — but the platform will still start. Closing it means calling `audit.verify()` during composition, which changes ADR-020's deliberate "build, then detect, then halt via the platform Kill Switch" behaviour and changes what TC-AUD-007 asserts. That is E11's ADR and the Board's design, not mine to change in an E07 branch. **Decide:** commission that change with E11 and the Board, or accept the on-demand form explicitly and require the periodic monitor (§8) before shadow.
- **PC-2 What this does *not* defend against — the Board's own list, unchanged.** [Committee: COUNCIL §3.1 "Residual after B"] (a) **The window since the last anchored head.** Commits that touch no control-invariant table are only covered by the count-based cadence, so a rewrite confined to that window is still invisible. (b) **The strength of the off-box anchor.** In dev/sim the "different principal" is a directory on the same host, written by the same process; a host-level attacker owns both stores and the anchor. The mechanism raises the effort — three consistent rewrites instead of one — and it does **not** make dev/sim tamper-proof. (c) **Nothing here is keyed.** An actor who can write both files and knows the algorithms is defeated only by the external witness, i.e. by O-54 being real. (d) **A simultaneous fresh start of both stores** (control store *and* audit store replaced by empty ones, anchor directory removed) presents as genesis on both sides; it is caught by ADR-020's rule that a scheduled publication may never create the first anchor for a non-empty chain, which depends on the anchor replica surviving — again O-54. **Decide:** accept that the dev/sim residual on T-61 remains "one host, one principal", and keep O-54 as a shadow entry condition in those words.
- **PC-3 What it costs at start-up, honestly.** [Verified: measured, §7] Per intent: 28.3 ms → 30.1 ms median and three extra audit rows — an audit append is an fsync'd transaction, so the cost scales with how often control invariants are written, not with volume of trading in general. At start-up: the witness lookup is a **linear scan of the audit chain** (9.0 ms at 20 000 events). That is small only because ADR-020 already loads and verifies the whole chain at open (1 082 ms at the same size) — start-up is already O(events) and this makes the constant slightly worse, not the complexity. **Both grow without bound**: compaction and retention are owed (O-55, O-111, O-135) and with anchoring they are now on the start-up path of the *trading* platform, not only of the audit service. **Decide:** treat compaction as a shadow entry condition rather than a nice-to-have, and note that no start-up SLO exists to measure this against [Open].
- **PC-4 The seat that designed this, built this and would validate this is still too small a set.** [Committee: SA-PO-4, unchanged] The Security Architect proposed the design and owns T-61; I built it as the E07 agent and wrote its ADR amendment and its tests. RT-05 — the red-team test that would independently probe T-61 — still does not exist and is scoped by the same seat. **Decide:** name a different seat (or the external pen-test supplier, H-10) to accept the residual and to sign RT-05, and do not let TC-DUR-007 be described as an independent test: it is the builder's own adversary model.
- **PC-5 A new way to stop the platform, deliberately built.** A control store whose head the audit chain cannot confirm **will not open**. That is the correct behaviour and it is also an availability risk: a lost or corrupt audit store now blocks trading, where before it only blocked the audit trail. The fix is always restore-then-verify; the temptation will always be to pass a flag. There is no such flag today, and the runbook that would say so does not exist [Open: O-134]. **Decide:** require the runbook before shadow, and record that "disable the check" is not an approved recovery action.
- **PC-6 I widened one attacker helper in another epic's test file.** [Verified: `test/quartets/test_tc_aud_audit.py::_rollback_consistently`] The rollback attacker now re-creates rows the truncated tail had deleted, because an ACCOUNT-level Kill Switch releases the lease and the old helper could not model that restore. TC-AUD-007 passes unchanged. It makes the modelled attacker stronger; it is still a change to E11's evidence and the reviewer should see it as one.
