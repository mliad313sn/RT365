### 3.2 DF-05 status [Verified at `a90b1ae`]

The row says "Idempotency, fencing token". The Control → Execution flow as implemented carries, in this order:

1. Plane guard: `ExecutionGateway._submit` first calls `self._guard.check_caller(Plane.EXECUTION, "order_command")` (`gateway.py` 286) [Source: 03; ADR-001].
2. **Command authorisation** (ADR-015, D-028/D-033): the pipeline signs (`pipeline.py` 260 `self.sign_command(command)`), the gateway verifies before anything else is disclosed (`_assert_authorised`, `gateway.py` 288); one-shot grant (`execution.consumed_authorisations`), maximum age `COMMAND_MAX_AGE = 5 min` (`gateway.py` 61), one order per `decision_id` (`execution.by_decision`). The key is created in the composition root and handed only to the pipeline (sign) and the gateway (verify); a caller-supplied `authorisation_key` is the vault/KMS path [Open: O-53] (`platform.py` 767–772).
3. Idempotency inbox `execution.by_idempotency_key` (ADR-003; `gateway.py` 291).
4. Per-intent live-order invariant `execution.by_intent` (ADR-014; `DuplicateIntentOrder`, S1 `execution.duplicate_order`).
5. Fencing: `LeaseStore.is_valid` (`lease.py` 82; `gateway.py` 332) [Source: 03; ADR-002].
6. **Permission oracle** `execution_permitted` (`platform.py` 774–814; ADR-015 D-029): Kill Switch scope > account HALTED / non-ACTIVE > tenant match > execution target consistent with account mode > decision provenance (intent known and in an executable state; decision known, same intent and policy version, APPROVED or REQUIRES_HUMAN_APPROVAL with an APPROVED approval record). The decision index and the intent tracker are **in memory** (`decisions: dict`, `IntentTracker`), which is why a restarted platform refuses every pre-restart intent as "unknown to the control plane" (TC-EX-011; O-113).
7. Durable, transactional registration of the indexes and the order row before the adapter is called (`gateway.py` 379–386; ADR-018), and the order row with its outbox event in one write (`_save`, 152–158).
8. Carrier: in dev/sim the pipeline publishes `order.command.v1` to the outbox (`pipeline.py` 268–270) and then calls `gateway.submit` **in-process** (`pipeline.py` 287); in deployment the carrier is the bus (ADR-005) across the `control` → `execution` NetworkPolicy egress (`control.yaml` 24–26) [Open: R-05].
9. Fail closed on the store: `StoreError` → S1 `execution.store_unavailable`, nothing reaches the broker (`gateway.py` 278–283; `alerts.yaml` 29; O-112).

Conclusion: DF-05 as drawn names two of nine controls and none of the tests (TC-EX-001..011, TC-DUR-001..004). The row is not wrong; it is out of date by two ADRs (ADR-014, ADR-015) and one accepted decision (ADR-018 / D-058) [Committee]. Proposed replacement text is in §8.1.

## 5. Views on ADR-018, O-113, O-115, O-122 and ROADMAP v1.1

### 5.1 ADR-018 — accept for dev/sim as the seam? **Yes**, and the seam is the right shape [Committee, on the code read in §2]
The `Store` protocol (`get/put/delete/items`, `next_sequence`, reentrant `transaction`, `verify`, `dump`, `close`, `correlation_id` on every mutation) is narrow enough to be re-implemented and wide enough for the four consumers; the consumers' interfaces did not change; every pre-existing test runs on the memory default; the restart quartet runs in CI [Verified: store.py; TC-DUR-001..004; TC-EX-011; TC-KS-010 in the 203]. Two code observations the ADR should state so that the Postgres adapter does not inherit them silently:
- (i) `Outbox.publish` notifies in-process subscribers **before** the enclosing transaction commits (`outbox.py` 39–43); in dev/sim a subscriber can act on an event whose transaction later rolls back. The relay path (`relay()`) is the deployment carrier, so this is a dev/sim-only caveat — but it must be written down [Verified].
- (ii) "A fencing counter can never be issued twice" holds because SQLite's `BEGIN IMMEDIATE` is a single global writer lock (`store.py` 166) and `_append` reads `MAX(seq)` under it (`store.py` 188). Neither property exists on Postgres by default — see the contract below [Verified].

**What the Postgres adapter contract must carry** (proposed §"Adapter contract" for ADR-018 or the ADR-010 revision; owner Integration Architect with Cloud Architect; acceptance quartet owner QA Lead, ids by the QA Lead):
1. **Transaction with row locks.** `transaction()` stays reentrant with rollback on any exception. Every read-then-write — `LeaseStore.acquire/preempt/renew/release`, `next_sequence`, `Inbox.process_once`, the gateway's index writes (`gateway.py` 379–386) — locks the rows it will write (`SELECT … FOR UPDATE`, insert-if-absent via `INSERT … ON CONFLICT DO NOTHING` then lock, or a per-key advisory lock keyed by `table:key`). Isolation at least READ COMMITTED with explicit row locks; SERIALIZABLE with retry is acceptable. A global writer lock is never assumed.
2. **Sequence.** `next_sequence(name)` is monotonic per name and is never reissued lower across failover, replica promotion or restore. Implement as a locked counter row inside the same transaction — **not** a native Postgres `SEQUENCE`, which is non-transactional (values survive rollback, which is harmless) but regresses after a restore from an older base backup (which is not). After any restore the adapter refuses to open until the counter exceeds the highest token observed in the journal and in the audit chain (a `verify` step).
3. **Journal head.** The journal `seq` and `prev` come from a single serialised allocator (a locked head row) so concurrent writers cannot fork the chain; the head is the anchoring point for O-110 (keyed HMAC or audit-head anchoring, O-54).
4. **Verify from a checkpoint.** O-111 compaction = a checkpoint row carrying the chain-head digest and a digest of the state snapshot; `verify()` at open replays from the last checkpoint; full replay stays available as an audit procedure; the time bound for verify-at-open is a measurement [Open: baseline] not a guess.
5. **Outbox relay.** Deliver-then-mark (as now) is **at-least-once** hand-off; exactly-once business effect is the consumer inbox's property. Rewrite the `relay()` docstring accordingly. One active relay per outbox (lease, or `FOR UPDATE SKIP LOCKED` claims); per-key ordering preserved; bus producer idempotent on `event_id`.
6. **Inbox claim row** before any topology that relaxes one-consumer-per-key (O-114, ADR-005 §Consumer assumption).
7. **Schema per service, role per service** (O-115): the execution role has no grant on control-plane schemas and vice versa; cross-service state travels only as events.
8. **Integrity scheme** per O-110 — Security & Privacy Board's choice, before shadow.
9. **Acceptance quartet on the compose topology** (O-117): positive — restart and failover on Postgres reproduce TC-DUR-001/TC-EX-011; negative — two OS processes contend for one account lease and exactly one holds it; abuse — a direct SQL edit is refused at read, a cross-schema read by the wrong role is denied; recovery — `kill -9` mid-transaction and a power-loss simulation leave no half-registered order, and a restore from an older backup is refused until the counters are bumped. Ids by the QA Lead.

### 5.2 O-113 — cancel-on-restart versus resume-on-restart (architecture view; the Trading Risk Committee advises, the Product Owner decides)
- **Keep cancel-on-restart through Gate C** (dev/sim, shadow, paper). It is the only behaviour the code can evidence today (TC-EX-011), it is fail-closed, and no baseline exists for the windows a resume rule needs [Verified: `platform.py` 797–799; O-33].
- **Define resume-with-re-decision as the Gate D target**, because "cancel every open order on every deploy or failover" is not an operable production posture (it converts every restart into forced market activity) but "resume without re-deciding" would re-execute a decision the Kill Switch, a limit change or stale data may have invalidated [Committee].
- **Re-decision rule (proposed text for O-113 / ADR-018 addendum):** on restart, for each order in an open state found in the durable store — (1) the intent tracker and the decision index are durable behind the seam (prerequisite; no resume before it); (2) query the broker (`query_order`, ADR-014) and adopt its state as external truth; (3) run the permission oracle (Kill Switch scope, halt, mode, tenant); (4) re-run the deterministic risk decision with the **current** policy version and fresh account/market snapshots, producing a new `DecisionRecord` (`risk.redecided.v1`, already an event name in `audit_pipeline`) — if APPROVED, continue managing the live order (no new broker order: the per-intent invariant forbids it); if not, cancel at the broker; (5) any failure in steps 2–4 (broker unavailable, stale data, unknown intent) drops to cancel-only with S1; (6) the age window within which a pre-restart intent may be resumed, and the freshness budget for step 4, are set by the Trading Risk Committee from measured baselines [Open: O-03] — never in this packet; (7) evidence: a restart quartet extending TC-EX-011 (positive resume, negative re-decision refuses, abuse replay under a new policy version, recovery broker unavailable during step 2).

### 5.3 O-115 — schema-per-service and outbox-per-service
Yes to both, and three things D-058 (a) implies that the design must state [Committee]:
- **Role per service and a physically separate instance for the Execution plane** — D-058 says "physically separate"; a schema in a shared instance is a logical, not physical, separation. The Control plane keeps its own instance per cell.
- **The Execution plane's read of Kill Switch state.** Today the oracle calls `platform.killswitch.blocks(...)` in-process. With separate stores the gateway's oracle must read Kill Switch state it can reach synchronously and fail closed when the state is unknown or stale — a replicated read model in the execution schema fed by `killswitch.*` events, carrying `as_of`/`state_known` (the R-23 residue, `RK-HALT-KS-UNKNOWN`). ADR-015 rejected "gateway keeps a local flag" as the sole mechanism because of the eventual-consistency window; the O-115 design must show how that window is closed (stale → refuse). This is the hardest part of O-115 and is not mentioned in the queue text.
- **Topology.** No storage or bus namespace is declared; `execution.yaml` egress admits only `execution`, `control`, vault (8200), the broker CIDR (443) and DNS, so an execution-plane Postgres must run inside the `execution` namespace or the policy gains a labelled store selector. `scripts/check_network_policies.py` should gain a rule: "no `analytics` or `control` pod reaches the execution store selector; no `analytics` pod reaches any store selector" (Cloud Architect + Security Architect; CODEOWNERS on the policies). The bus's namespace and its policies are [Open: R-05].

### 8.3 ADR-018 addendum (build agent E07 / Backend Lead; reviewers Trading Domain Lead, Integration Architect)
```
## Adapter contract (added 2026-09-08 on the ARB's recommendation, COUNCIL_2026-09-08_gate_B_arb_docs.md §5.1)
1. Row locks: every read-then-write locks its rows (SELECT … FOR UPDATE / insert-if-absent then lock / per-key advisory lock); no global writer lock is assumed.
2. Sequences are locked counter rows, transactional, monotonic per name, never reissued lower across failover, promotion or restore; after a restore the store refuses to open until each counter exceeds the highest value in the journal and the audit chain.
3. The journal head is a single serialised allocator; it is the anchoring point (O-110, O-54).
4. verify() replays from the last checkpoint (O-111); full replay remains an audit procedure; verify-at-open time is measured, not assumed.
5. Outbox relay is at-least-once hand-off (deliver, then mark); exactly-once business effect is the consumer inbox's property; one active relay per outbox; per-key ordering; producer idempotent on event_id.
6. Inbox claim row before any topology that relaxes one consumer per key (O-114).
7. Schema and role per service (O-115); cross-service state travels only as events.
8. Integrity scheme per the Security & Privacy Board (O-110) before shadow.
9. Acceptance quartet on the compose topology (O-117): restart/failover; two OS processes contend for one lease; SQL edit and cross-schema read refused; kill -9 / power-loss / restore-then-refuse.
## Dev/sim caveats stated
(i) Outbox.publish notifies in-process subscribers before the enclosing transaction commits; the relay is the deployment carrier. (ii) "A fencing counter is never issued twice" relies on SQLite's BEGIN IMMEDIATE global writer lock; contract items 1–2 replace it on Postgres.
```
