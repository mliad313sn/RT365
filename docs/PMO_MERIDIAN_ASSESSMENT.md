# Meridian IT-PMO — real-case efficiency to drive a project, and what to improve

| Owner | Reviewer (different line) | Approving body | First gate | Status |
|---|---|---|---|---|
| Product Owner (delegate agent, with the CAB chair and counsel-platform-reliability views) | Program Orchestrator | Product Owner (D-049) | A | v1.1 — 2026-09-08: re-tested on Meridian 5.10.0; all twelve improvements delivered upstream; new requirements V-1..V-12 (§7, §8) |

Assessed by **using it**, not by reading it: Meridian 5.9.0 (commit 77c4b49) was cloned, tested, seeded, run, loaded with this programme through its API (16 projects, gates A–F, 86 RAID items, 14 decisions, 21 actions), exported and screenshotted (docs/PMO.md §4). Every statement below is [Verified] on that run, [Source: Meridian docs/NN] when it comes from Meridian's own committee record, or [Committee] when it is our judgement.

## 1. Verdict in one paragraph
Meridian is an unusually well-governed piece of software for a portfolio office: authority is data (group/site/admin/viewer decided server-side), every mutation is audited inside its own transaction, segregation of duties is enforced on change requests and gates, tolerances and exceptions exist, meetings are generated from the portfolio state and their decisions and actions land back on projects, and an ordered end-to-end journey test replays the life of a new organisation on every `npm test` (449 tests pass) [Verified; Source: Meridian docs/32]. **To drive a real project it is efficient as the governance record and meeting engine at programme and site level, and inefficient as the place where engineering delivery actually happens**: its process model is fixed (four gates, six phases), its public API is read-only, it has no traceability, evidence or work-tracking concepts, and its own market committee states that it has never run a real portfolio for a year and has no vendor, backup or second instance [Source: Meridian docs/24 §7, SECURITY.md]. For RoboTrader that division is exactly right: the ledgers and CI hold the engineering truth, Meridian holds the portfolio rhythm (ADR-017).

## 2. What it does well (measured)
| Capability | Evidence | Value for a real project |
|---|---|---|
| Authority as data; SoD on change control and gates | `shared/rbac.js`; PR-03 fix in 5.9.0; journey test §7 | The raiser can never approve their own change; a site cannot decide its own demand — real controls, not conventions |
| Append-only audit with before/after images | `server/src/audit.js`; `GET /api/audit` returned every load action with actor and detail | An auditor can replay how the portfolio got there; a change that is not audited does not commit |
| Generated meetings | `Meetings & decisions`: our weekly appeared with 16 projects, agenda built from actions overdue, projects off track, RAID reviews | Removes the deck-writing week; the minutes are the data |
| Stage gates with evidence, tolerances, business case reconfirmation, closure with named owners, lessons | migrations 024–033; docs/26 PM-01..PM-08 closed | PRINCE2/ISO 21502 discipline that most trackers lack |
| Idempotent, versioned writes | `row_version` + 409 on stale writes; PR-02 refuses a PATCH with no recognised field | Two writers never silently overwrite; our sync could be made idempotent on top of it |
| Reversibility | `GET /api/admin/archive` (1,529 rows / 47 tables on our book), `npm run restore` | Data gets out without the vendor |
| Self-contained | PGlite (PostgreSQL in WASM) with no server to install; Windows service installer | A PMO can run it on a laptop or a VM in an hour |

## 3. Where it is not yet fit for a real project (measured or stated by its own committees)
| # | Finding | Evidence | Consequence for a real project |
|---|---|---|---|
| M-01 | The one-minute quick start (`npm install && npm run seed && npm run dev`) gives an **in-memory** book: without `PGLITE_DIR` (only set in `.env.example`, which nothing loads) `openPglite(null)` creates `new PGlite()` in memory, so the seed is lost and the server starts empty | [Verified] `server/src/db.js:152`; login refused after seed until `PGLITE_DIR` was exported | First-hour failure for every newcomer; data loss if someone runs a real book that way |
| M-02 | With `PGLITE_DIR` set on a fresh clone, PGlite `mkdirSync` is not recursive: `ENOENT … server/.data/pgdata` until `server/.data` is created by hand | [Verified] seed and server both crash | Same as M-01 |
| M-03 | `npm run dev` before `npm run build` serves `Cannot GET /` (static mount is skipped when `web/dist` is absent); the README says the app is on :4173 | [Verified] `server/src/index.js:172-189` | Confusing first run; a `dev` script should build or proxy |
| M-04 | **Fixed process model**: four gates (Mandate, Design authority, Readiness, Benefits) and six phases are scaffolded on every project and cannot be replaced by the organisation's gate ladder; our six gates had to be added as plain milestones next to Meridian's four | [Verified] `shared/engine.js` GATES/PHASES; screenshot docs/PMO/meridian_project.png | Any organisation with its own gate model runs two models in parallel; evidence and phase advancement bind to the wrong one |
| M-05 | **Public API is read-only** (`/api/v1/portfolio`, `/api/v1/audit`); every write goes through undocumented session routes (144 of them) that the web client uses. No OpenAPI for them, no upsert, no external-id field on RAID/milestones/decisions, so an integrator encodes identity in titles (`[O-11] …`) | [Verified] docs/openapi.v1.json (4 paths); our sync | Bidirectional integration (Jira, ADO, CI, ledgers like ours) is not possible without scraping internal routes; INT-01/INT-13 open [Source: docs/27] |
| M-06 | No traceability, test-evidence or requirement concept; "evidence" is a document link per gate | [Verified] schema: `document`, no requirement/test tables | Regulated engineering programmes keep RTM and evidence elsewhere; Meridian cannot answer "which test proves this gate criterion" |
| M-07 | Work tracking is a light board (`work_item`) with no link to commits, PRs or CI; progress is "reported by the source system" | [Verified] screenshot: completion 0% "reported" | Progress must be typed in; EVM reads typed percentages |
| M-08 | Zero real usage, no vendor, no on-call; three blocking operational findings are the operator's (tested backup G-01, second instance, written security policy); PGlite is single-connection and a hard kill can leave the data directory unopenable | [Source: docs/24 §2 and §6, SECURITY.md, README "Do not hard-kill"] | A real portfolio needs PostgreSQL, backups proven by restore, and someone accountable on a Sunday |
| M-09 | Single maintainer, no releases or tags, `package.json` 5.9.0 while the published OpenAPI says 5.3.0; `verify.yml` is the only CI | [Verified] git log, docs/openapi.v1.json | Key-person risk; version drift between artefacts |
| M-10 | Demo credentials seeded by default and public; SoD admin exemption is deliberate break-glass | [Source: SECURITY.md] | Must be changed on day one; admins can self-approve |
| M-11 | Half the documentation (committee records, the "why") is French; UI bilingual | [Source: README] | Slower adoption outside francophone teams |
| M-12 | Capacity is FTE-only (no skills), no stakeholder register, no contract/supplier performance, no communication plan, finish-to-start dependencies only | [Source: docs/26 PM-05, PM-07, PM-10, PM-11, PM-12 open] | Adequate for an IT PMO; thin for industrial or vendor-heavy programmes |

## 4. Efficiency judgement for driving a project (real case)
| Question a sponsor asks | Answer with Meridian today |
|---|---|
| Can I see the portfolio, what is off track and what needs a decision this week, without a deck? | **Yes** — the executive view, the generated weekly and the decisions-owed panel do this well [Verified] |
| Can the governance trail survive an audit? | **Yes** for what is in Meridian (append-only audit, SoD, versioned rows); **no** for engineering evidence, which lives elsewhere |
| Can delivery teams work in it day to day? | **No** — it sits above the team tools by design; without INT-10/INT-11/INT-13 progress and cost are typed in |
| Can I plug it into what I already run (Jira, ADO, ERP, CI, a repo of ledgers like ours)? | **Read only**: BI tools via `reporting.*` views and `/api/v1`; writes need the session API or CSV import (projects, people, milestones) |
| Can I trust it in production? | Not yet as shipped: PGlite in memory by default, no backup story, single maintainer, no vendor [Source: docs/24]. With PostgreSQL, a restore-tested backup and a second instance, the software itself is sound (449 tests, nine static gates, journey test) |
| Time to first useful state | About one hour once the four setup traps above are known (M-01..M-03 cost this assessment ~40 minutes); loading 16 projects, 86 RAID rows and a weekly by API took under a minute |

**Net:** Meridian is efficient as the *governance and rhythm layer* of a real programme (it replaces the spreadsheet, the deck and the untraceable meeting) and, at this version, not sufficient as the *delivery system*; it needs a write API and integrations to stop being a place where truth is re-typed.

## 8. Requirements for Meridian as the tool that drives projects to business value

The owner's aim is a tool that does not only prove a project was **run well** but that it was **worth doing** and **delivered what it promised**. Meridian already has more of that skeleton than most portfolio tools: `business_case` (expected cost, expected benefit, the basis for both, and a reconfirmation at a named gate), `benefit` (kind, measure, unit, baseline, target, actual, owner, realisation date, and a status separate from the measurement, reviewed by a group-level act, migration 008), `lesson`, `stakeholder`, `comms_plan`, `rollout_wave`, `project_tolerance`, `project_exception` and a closure that refuses to complete without a named benefits owner [Verified: schema and `routes/portfolio.js`]. The requirements below therefore do not propose a value model — they close the gaps between the model and the way value actually gets realised and reported. Each carries a measurable acceptance criterion; effort S = days, M = weeks, L = a release.

| # | Requirement | Why a real project needs it | Acceptance criterion (measurable) | Effort | Priority |
|---|---|---|---|---|---|
| **V-1** | **Value objects in the write API v1**: `PUT /api/v1/business-case/{externalId}` and `/benefits/{externalId}` under `write:portfolio`, with the same external-id, idempotency and audit rules as the delivery collections | REQ-02 made delivery facts syncable from the field repository; value facts still have to be typed into the UI, so the one thing an executive reads is the one thing that goes stale. Our own loader pushes 256 delivery writes and cannot push a single benefit | An external integration creates and updates a business case and three benefits by external id; a second identical run makes zero creating writes; both appear in `/api/v1/portfolio` and in the audit trail under the integration's name | S | highest |
| **V-2** | **The benefit review is a scheduled act, not a hope**: when `realise_on` passes, an agenda item appears on the owning board's next occurrence, and an unreviewed benefit past its date is a portfolio exception like a tolerance breach | Benefits realise after closure, when the project team has dispersed. A date in a table that nothing chases is how value reporting dies in every organisation | A benefit with `realise_on` in the past appears automatically on the next meeting agenda and in the exception list; recording a `benefit.review` clears it; the trail shows who reviewed and against which measurement | M | highest |
| **V-3** | **The business case is re-confirmed at every gate, and the gate cannot pass without it**: extend the existing `reconfirmed_gate` into a gate criterion the ladder enforces, comparing expected cost and benefit at that gate against the last version | `business_case` already carries the reconfirmation fields; nothing forces them. A stop/continue decision at each gate is the single highest-value control a PMO owns, and it is the one most often skipped | Passing a gate on a project whose case has not been reconfirmed at that gate is refused with a named reason; the gate record shows the case version, the delta against the previous one and who reconfirmed | S | highest |
| **V-4** | **Forecast versus realised, as one report**: a value report per programme showing, per project, expected benefit from the case against measured benefit actuals in their own units, with the count of benefits by status and the ones overdue for review | The two halves exist in two tables and are never confronted. The confrontation is the report the sponsor wants and the one that changes behaviour | One page and one `/api/v1` resource returning, per project: case expected cost and benefit, each benefit's baseline/target/actual with unit, status, review age; no derived money conversion of non-money units | M | high |
| **V-5** | **Portfolio prioritisation by value and risk, with capacity**: score `demand` and live projects on the value the case claims, the confidence in it, the risk exposure from RAID and the capacity they consume, and show the ordered list against available capacity | Choosing what not to do is where a portfolio creates most of its value. Meridian ranks nothing today; `demand` carries no score | A ranked list per programme with every input visible and editable, a stated weighting, and a line showing where committed capacity runs out; changing a weight re-ranks and is audited | M | high |
| **V-6** | **Adoption and outcome telemetry per rollout wave**: `rollout_wave` gains measured adoption (who actually uses the change) and a link from wave to the benefits it is supposed to move | A delivered change that nobody adopts realises nothing, and adoption is the earliest signal that a forecast benefit is in trouble — months before `realise_on` | Each wave carries an adoption measure with its source and date; a benefit's page shows the adoption trend of the waves feeding it; a wave with adoption below its own threshold raises an exception | M | medium |
| **V-7** | **Lessons become a checklist, not an archive**: `lesson` rows are tagged to a gate and offered as a checklist at the same gate on later projects, with a record of whether each was considered | Lessons that are only stored are lessons not learned; the moment of use is the next gate of the same kind | At a gate, the reviewer sees the lessons tagged to that gate from closed projects of the same programme and records considered/not-applicable per lesson; the gate record keeps that list | S | medium |
| **V-8** | ~~One ladder per project~~ **withdrawn as published; re-filed narrower.** Meridian scaffolds one ladder, chosen by the programme's `gateModel`; a programme that declares none gets the default four-gate ladder. The genuine request that remains: **a book created before migration 036 cannot be migrated onto a programme ladder afterwards** | the fix is free for a new book and unavailable for an existing one, which is every book that predates the feature | a programme whose ladder is set after its projects exist can adopt it without duplicating or destroying dated milestones and their evidence | S | medium |
| **V-9** | **Governance quality signals on the portfolio page**: decision latency (raised to decided), action ageing, gate cycle time, RAID review compliance, exception age | A PMO that cannot see its own throughput cannot improve it, and these five are the leading indicators of a programme that is quietly stalling | Each metric computed from existing timestamps, shown per programme with its trend, and available on `/api/v1`; no new data entry required | S | medium |
| **V-10** | **Evidence provenance for gate criteria**: a criterion may cite an external evidence reference (repository, commit, artefact, checksum) that the reviewer confirms, instead of a document link | REQ-04 gave criteria an independent reviewer; the evidence is still a document link. Our gates read CI-evidenced commits, and a link to a mutable document is not evidence of anything | A criterion can carry a typed external reference with a commit or checksum; the gate record shows what was cited and by whom; changing the reference after the gate is a new version, never an edit | M | medium |
| **V-11** | **A value dashboard for the executive**: one page per portfolio — spend against case, benefits by status, overdue reviews, top risks by exposure, gates due, exceptions open | The current portfolio view answers "is it on time and on budget"; nobody without the tool open can answer "is it worth it" | One page, printable, generated from the objects above with no manual entry, and a snapshot stored per reporting period so a claim made in March can be re-read in December | M | medium |
| **V-12** | **A public reference implementation of the loop we ran**: package `scripts/rt365-review.mjs` and the request register as a documented pattern any field repository can adopt | The strongest thing this product now has is evidence that a real programme's findings reached a release in a day. That is a capability, not an anecdote, and it should be reusable | A documented schema and command let a second repository file its register and see its requests tracked, without Meridian-specific code in that repository | S | high |

**Correction, 2026-09-08 (same day):** this was published as a Meridian defect and it is ours. `shared/engine.js::normaliseGateModel` and `server/src/wbs.js` scaffold **one** ladder, chosen by the programme's `gateModel`, and `POST /api/admin/programmes` has accepted that field since migration 036. Our loader never sent it, so our projects were born with Meridian's default four-gate ladder alongside the six milestones we then created. `scripts/meridian_sync.py` now declares Gate A–F on the programme (TC-PMO-002). Meridian's own answer to us said as much, and we filed it against them anyway [Source: Meridian shared/engine.js, server/src/routes/admin.js].

Not proposed, deliberately: an OKR object (the case plus benefits already carry objective, measure and target, and a second vocabulary would split the truth), a money-normalised portfolio value (migration 008 is right that value is not always money-shaped, and forcing a currency invents numbers), and any AI feature — the governance value here comes from the record being trustworthy, and nothing in this list needs a model.

**Filing:** these are for Meridian's Product Owner through the register mechanism it created (`docs/requests/rt365.json`, REQ-14 onwards). They are recorded here and in docs/IMPROVEMENT_REGISTER.md §D; filing them upstream as issues is a human act on the owner's account [Open].
