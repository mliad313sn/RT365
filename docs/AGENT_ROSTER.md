## Principle [Source: 00, 13; Committee]
Every prompt in `goals/` is an agent; every agent is generated from its prompt (`scripts/generate_agents.py`, drift-checked in CI) so that the prompt stays the single source of truth. Agents are organised by the Three Lines of Defense: an agent never sits in two lines for one control, the builder is never the sole approver, and 3rd-line agents own nothing they review. A PreToolUse hook (`scripts/agent_guard.py`, declared in the project `.claude/settings.json` and repeated in each agent's frontmatter) confines each agent's edits to the paths its prompt says it owns plus the shared ledgers. Probes of 2026-09-08 (O-58): frontmatter hooks are not honoured for sub-agents, but the project-level hook is, and the harness passes `agent_type` in the payload, so the roster is enforced for Edit/Write of every sub-agent; Bash writes are not inspected (R-46). CODEOWNERS, branch protection and CI remain the controls of record.

## Skilled, informed, experienced (owner instruction 2026-09-08)
Every committee role agent carries an expertise profile (`goals/profiles/NN_<role>.md`): expertise and standards (skilled), a mandatory reading list of repository artefacts (informed), known failure modes and decision heuristics (experienced). Seven independent **approver** agents (`goals/approvers/`) chair the councils with a delegated technical approval scope and never approve what they authored or reviewed; nine specialist **counsellors** (`goals/counsel/`) advise any council and never approve. The human Product Owner decides every human decision, gate and risk acceptance (docs/PRODUCT_OWNER.md, D-039). Adding an approver or counsellor = one prompt file + `make agents`.

## MCP servers the agents may use
| Server | Config | Transport | Capability class | Owner / approver | Notes |
|---|---|---|---|---|---|
| `rt365-sim` | `.mcp.json` | stdio (`rt365 mcp-serve --env sim`) | the six registered tools only (`mcp/policies/tool_registry.signed.json`); one write-class tool that writes to the intent queue | Backend Lead / MCP Security Agent (registration pending, REVIEW_C3) | Identity is issued by the host process for `agent-claude-code` on the sim tenant; every call passes the full ToolRuntime chain (TC-AI-012..015). Refuses to start outside `RT_ENV=sim` and without the signed registry (TC-PKG-002/003). |
| GitHub (harness-provided) | Claude Code / Claude.ai connector, not repository config | — | repository read/write, PR review | Program Orchestrator | Delivery tooling for the agents; it is not a trading component and has no route into the platform. |

Forbidden for any agent [Source: 04]: a broker MCP server, a vault/secrets server, a shell or arbitrary-web server in the agent context, or any server that can change limits, mode or audit. Proposals for new servers go through the MCP tool registration process in docs/MCP_TOOL_CATALOG.md.

## How to use the roster
- Claude Code loads `.claude/agents/*.md` automatically; invoke an agent by name (for example `product-owner`, `chief-risk-agent`, `build-e05`, `gate-c`, `independent-validation-agent`) or let the description route the task.
- Committee protocol per session: accountable role agent → challenging agent from a different line → `independent-validation-agent`; write the packet to `docs/SESSIONS/`.
- Decision packs (`goals/decisions/`) and external workflows (`goals/external/`) are tasks executed by the owning role agent, not separate agents.
- Regenerate after editing any `goals/` prompt: `python3 scripts/generate_agents.py`; CI runs `--check`.
