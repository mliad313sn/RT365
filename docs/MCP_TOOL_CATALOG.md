**Registration status [Committee: O-35; D-039].** No tool in this catalogue is registered, approved or authorised for anything beyond dev/sim. The six capabilities are *implemented* in sim behind `mcp_servers.runtime.ToolRuntime` and are carried in a **sim fixture** registry whose signature explicitly embodies no approval. The approving act belongs to the Security & Privacy Board (recommending) and the Product Owner (deciding), never to this document's owner: the MCP Security Agent wrote these specifications and therefore may not approve them [Source: 13; blueprint 00 "never self-certify"]. The registry's own signing code enforces the same rule from the other side — `prepare_envelope` refuses to sign non-fixture content while any `approval_record` contains "pending" — so the committed registry cannot be re-signed as a real artefact until the approval decision exists [Verified 2026-09-08: `mcp/servers/mcp_servers/registry.py`].

Allowed capabilities [Source: 04]; attributes [Committee]. Anything not listed is forbidden. **What "structurally impossible" covers, and what it does not** [Verified 2026-09-08; REVIEW_2026-09-08_security_plan_mcp §4 row 11, MSA-F-3]: it covers the closed six-tool allowlist in a signed registry, an import scan that keeps execution, broker, vault, Kill Switch, policy-mutation and signing modules out of `mcp_servers` (TC-AI-005), a transport that ignores client-asserted identity (TC-AI-014), and the absence of any network I/O in a handler. It does **not** yet cover the runtime sandbox: `filesystem: read-only`, `shell: absent` and `secrets_mount: none` are declarations in `mcp/policies/runtime.yaml` that `rt365 check` and `verify_tool_registry.py` compare against themselves; nothing enforces them at runtime, in dev/sim the runtime shares a process with the BFF on a writable filesystem, and the import scan reads `mcp_servers/*.py` while the registered handlers live in the BFF composition module [Open: H-05; REVIEW_C3 F-20].

Forbidden [Source: 04]: direct broker calls, arbitrary code execution, shell access, secret retrieval, risk-policy mutation, audit deletion, unrestricted web access, dynamic installation in production.

Registration process: proposal → threat-model delta → sandbox tests (injection corpus, escalation, oversize payload, revoked call) → **approval decision by the Security & Privacy Board / Product Owner, recorded in DECISION_LOG (never by the specifying role)** → signature under a ceremony key → per-tenant allowlist → quarterly re-attestation. **No step of this process has been completed for any of the six tools** [Open: O-35].

Dev/sim status [Committee]: all six tools are implemented behind `mcp_servers.runtime.ToolRuntime` (identity → signed registry → revocation → allowlist → quota → payload → input schema → handler deadline → output schema → canary → provenance delimiting → tamper-evident log). Independent review: SESSIONS/REVIEW_C3_mcp_security_agent.md (which **rejected** the six registrations as currently signed) and SESSIONS/REVIEW_2026-09-08_security_plan_mcp.md.

**Signing and trust state [Verified 2026-09-08 at `40bcb51`].**
- The committed registry `mcp/policies/tool_registry.signed.json` is **HMAC-SHA256 signed under the documented dev key `dev-key-v0`**, tagged `environment_tag: sim`, `fixture: true`. It is refused outside dev/sim from any source including an environment variable, and `verify_tool_registry.py --production` fails by design [Open: O-127].
- The public trust set `mcp/policies/trust/registry_keys.json` **does not exist in the tree**. Absent means an empty trust set, which refuses every Ed25519 signature — fail closed by design, and also the reason the asymmetric path cannot be exercised end to end today [Open: O-141, O-126].
- Order before shadow, each step gated on the one above and each needing a human act: tool approval (O-35) → key ceremony with three distinct humans (H-20) → trust set created and distributed by runbook, CODEOWNERS and installer (O-141, O-126) → registry re-signed under the ceremony key (O-127) → revocation drill run (H-19). **The author/reviewer separation of the trust-set file itself is unresolved**: its default location sits inside this role's write scope, so either CODEOWNERS names the Security Architect as author and the MCP Security Agent as reviewer for `mcp/policies/trust/`, or the file moves to `security/signing/trust/` [Open: proposed as MSA-9 in REVIEW_2026-09-08_security_plan_mcp §8].
- The environment label is bound to the registry's `environment_tag` **only when `RT_ENV` is set**; with no label an Ed25519-signed non-fixture registry of any tag loads. Unreachable while O-127 and O-141 hold; must be closed before either closes [Open: MSA-1; quartet in REVIEW_2026-09-08_security_plan_mcp §6.1].

**Emergency revocation [Source: 04].** Revoking the registry signature makes every server refuse at the next call, across restarts, and restoring requires two distinct approvers. This is covered by tests (TC-AI-003, TC-AI-004, TC-AI-008, TC-AI-015) and **has never been drilled**: `mcp/policies/README.md` and `runtime.yaml` promise a quarterly drill and no drill record exists anywhere [Open: H-19]. A test is not a drill; see `mcp/policies/README.md` for the procedure and the record a drill must produce.

**Per-tenant allowlists [Committee: D-061 (8), O-123].** One `allowlist.<tenant>.yaml` per tenant under `mcp/policies`, with a filename/content cross-check and duplicate refusal. Only `tenant-sim` ships; the second tenant stays a test fixture under `test/fixtures/policies/` until a tenant onboarding process exists, because a per-tenant allowlist is an approval record and shipping one inside the distributed bundle would place an unapproved policy in a signed artefact — while per-tenant allowlists are **not covered by the registry signature** [Open: O-172]. Two conditions carried by this role: a negative test that the second-tenant fixture is refused outside dev/sim [Open: O-123, MSA-5], and a signature over per-tenant allowlists before any real tenant [Open: O-172 — the decision, owed before shadow, whether the registry signature covers the policy directory or each policy file is pinned; both citations here read O-81 until 2026-09-09, which is the asymmetric-verification, trust-set and algorithm-allowlist item (RAID_LOG O-81) and covers neither claim].

Both transports call `ToolRuntime.call`; there is no third path to a tool [Verified 2026-09-08]. Forbidden servers for any agent context: broker, vault/secrets, shell, arbitrary web, limit/mode/audit mutation.

**Known limits of the runtime, stated so no reader over-reads the table above** [Verified 2026-09-08; REVIEW_2026-09-08_security_plan_mcp §4]:
- The per-tool `timeout_s` is a **caller-side deadline**, not a pre-emptive one: the caller is released and the result discarded, but the handler thread is not interrupted and keeps a worker slot. Non-returning handlers can exhaust the pool [Open: R-20, MSA-2]. No test covers the timeout.
- The in-process `EgressPolicy` is loaded by the composition root and is **not on the tool call path**; egress is evidenced today by the NetworkPolicy manifests and their union checker, not by an in-process check [Open: REVIEW_C3 F-20].
- Provenance labelling is applied in the runtime to outputs whose provenance is not trusted for decisions; the injection **corpus** named in the registration process above does not exist [Open: O-29, R-13].
- No number in this catalogue is a decided threshold: quotas, timeouts and payload limits are the fixture registry's values [Open].
